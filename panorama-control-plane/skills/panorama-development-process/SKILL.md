name: panorama-development-process
description: 在已经采用 .panorama/process.json 开发过程规范的项目中，用本地 CLI 开始、检查、评估、完成或接续开发任务。也用于用户明确要求按 Panorama 开发规范接入项目。普通代码解释、未接入项目的一般修改及全景展示不触发此技能。
---

在项目里完成用户授权的开发工作，同时保存可复核的开发过程证据。先读项目的 `.panorama/DEVELOPMENT.md`；CLI 与数据根信息以当前项目配置和实际命令结果为准。项目尚未接入时，按 [项目指引](references/project-guide.md) 中的初始化说明准备明确的输入范围和检查命令。

首次接入先用 `preflight` 生成配置草稿并核对排除范围、运行时和能力缺口。固定本机入口的 `doctor` 校验安装及 Node/Python；实际 runner 仍由项目明确登记。预检不执行项目脚本，发现脚本名称不等于已有检查证据。空项目可先登记无 runner 的工程准备工作，完成并收束后再登记首个检查器。

用户授权在任务中持续有效。不要为每个本地检查再次请求确认。任务明确且可逆时继续实施；缺少业务信息时先做独立可完成的部分。项目规范与此技能不增加额外人工批准层。

开始代码修改前调用 `begin`，说明目标、预期结果、影响模块、预计文件范围、验收项及对应对象。使用返回的 Structure 工作项 ID；已存在的任务先 `resume`，保留原始基线。Harness 管理的任务保持只读关联，沿其原有流程执行，不创建第二个活动任务代替它。

需要减少重复字段时用 `draft --for begin|check|review|finish` 复用已登记信息，回读默认值来源并补齐 null；`validate --for ... --input ...` 只校验请求和声明绑定，不执行任务或判断当前证据。已有完整请求可直接使用原入口。多个兼容验收项需按实际覆盖明确选择，不能把候选全选当成检查覆盖。草稿不会替你给出评审结果、清空未完成事项或判断公开影响。

正常路径是 `begin → 开发 → scan/check → finish`。只有与本次要求相关的 runner 才执行；文档任务不自动扩大为全局构建或视觉验收。编辑可以用 Codex 原生工具，编辑后 `scan` 检查实际范围、条件规则和范围外变化。CLI 只声明事后扫描，不能描述成写入前拦截。

P7 的 `catalog` 提供文档维护、公开行为修复、留存产物配方及领域合同；`draft --for begin --recipe <ID>` 生成可编辑建议。`matrix --work <ID>` 重新观察规则适用性及声明覆盖，不建立通过记录。配方不豁免接口文档中的公开承诺，TAR/GLB 完整性不支持视觉或内容质量验收。

显式启用 bootstrap v2 后，为对象登记 format/scopeId，为每项机器验收选择合同 claims，不能自动全选属性。先核对检查器递归导入、配置、样本、工具和实际对象依赖，再声明 scope 完整性依据；无法确认时用 incomplete，退回全部声明输入并保留未观察依赖。新证据要求真实退出状态和有效结构报告；退出 0 但缺少报告仍不能通过。历史 v1/v2 工作保持原语义，升级使用配置计划和新的工作。

机器检查使用注册的可执行文件与参数，保留实际退出码。留存产物必须用自己的对象身份和对应检查；fresh build 需要新对象，不得用一次构建替代已有产物验收。项目外输入先注册路径与选择范围，不能从外部 Receipt 自动授权读取。

如果需要由 coding agent 核对说明文档，实际阅读后用 `review` 记录方法、发现和具体对象。此通道仅代表 coding agent 声明，不能冒充 human。需要人工来源的规则保持未验证，直到有合适来源的证据。`import` 保存外部声明，不因自报 local_capture、observed 或 human 而获得本地可信凭据。

`finish` 提交结果、未完成事项与接续笔记，再看逐项 Assessment。缺证、过期、冲突、范围外变化或必需事项未完成时继续处理。若选择某些 Receipt 取代相反结论，显式列出 `selection.receiptIds` 和理由；历史失败仍保存。不得通过修改历史摘要、规则强度或工作定义来获得通过。

新任务上下文先 `resume`，读取原始目标与基线、当前文件变化、实际进程状态、未完成事项和证据缺口。进程中断不表示检查已经完成，也不表示原进程仍可接着执行。`resume` 从不重跑命令，需要重跑时明确调用 `check`。

变更输入范围、runner 或工具路径时先 `config-plan` 回读差异与阻塞，再 `config-apply` 使用该计划切换；不能直接改 local.json 或用 init 覆盖配置。未收束工作和待恢复执行会阻止切换，不能为消除阻塞补写完成。工程准备完成后的新模块通过 `refreshModules: true` 调用固定 Structure 的保留式重扫登记，不直接编辑内部模块账本。

遇到 `CONFIGURATION_RECOVERY_REQUIRED`，用 `config-status` 定位同一次操作，再 `config-recover`；该过程不重跑业务检查。回退使用 `restoreRevisionId` 创建新修订，旧配置、Receipt 和基线继续保留。历史工作按照原修订解释；当前撤销的范围或工具保持 unknown，不能用旧配置恢复读取授权。停用接入用 `detach`，保留用户指引和历史记录。

日常可加 `--format summary` 阅读工作与逐项缺口，保留真实业务退出码和日志目录；需要完整记录时使用默认 JSON。`nextActions` 仅提供后续参数，不表示已执行。定位耗时时加 `--timings on`，分别读取父进程与 workerTiming；不要把重叠区间相加，也不要用一次测量推断效率提升。

交付时区别过程要求得到支持、Structure 工作项 done、正式验收与部署。本地 CLI 的结果不建立正式 Acceptance/Gate，也不证明宿主拦截、人工身份认证或整个运行环境已冻结。
