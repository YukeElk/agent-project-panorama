# V0.5.1 Event Head Recovery Policy Adapter 迭代方案

状态：Implemented and Locally Validated；作为内部里程碑保留，公开发布已延迟

基线：Agent Project Panorama `v0.5.0`，Tag target
`55669d80a1e2d3dbe9d35de9c7be5e348b76d70b`

内部里程碑：`v0.5.1` capability checkpoint（无公开 Tag/Release）

建议分支：`agent/v0.5.1-event-head-policy-adapter`

## 1. 决策摘要

V0.5.1 建议只实现一个 Delegated Policy Operation Adapter：`event_head.recover`，同时建立后续
Operation Adapter 可复用的故障注入与一致性验证模板。

本切片不同时接入 `engineering_event.record`、Continuous Observation、Verification Receipt、Studio、
INIT、Renderer、View IR 或 Export。`event_head.recover` 的 fail-closed 门禁已经本地通过；形成内部基线
Commit 并通过远程 CI 后即可进入 V0.6 多视图工作，不要求先单独公开发布 V0.5.1。

推荐理由：

1. V0.5.0 已完成 Event Core、Approval Policy Core 和 opt-in Proposal/Apply Outbox，但 allowlist 中还没有
   一个真实 Operation Adapter 完成端到端接入；
2. Event Head 是派生索引，恢复操作只允许重建 `stream-head.json`，不修改已有 Event、Panorama Core 或业务
   项目，影响范围最窄；
3. `approval-policy.schema.v0.1` 已为 `event_head.recover` 冻结完整 `recoveryRules`，授权边界比
   `engineering_event.record` 更明确；
4. 该切片可以先证明 Use Allocation、真实副作用、Event/Receipt 双写、Ledger 推进和崩溃恢复，再把同一模板
   用于更高价值但范围更复杂的轨迹记录 Adapter；
5. 现有显式 `recover_store_head` 需要在 Policy 路径前增加严格 Head State 分类，确保 Head ahead、身份错配、
   Hash mismatch、重复 Sequence、Fork 或歧义不会被自动“修复”。

## 2. 候选比较

| 候选 | 用户价值 | 合同成熟度 | 副作用范围 | 主要缺口 | 决策 |
| --- | --- | --- | --- | --- | --- |
| `event_head.recover` | 中；减少确定性恢复的重复确认 | 高；已有完整 `recoveryRules` | 只重建派生 Head | 严格状态分类、Adapter 事务恢复 | **V0.5.1 推荐** |
| `engineering_event.record` | 高；直接支撑轨迹记录 | 中低 | 追加正式 Event | 缺少 Event Type、Actor/Producer、Authority、Label Strength 的精确 Policy Scope；需 Currentness Verifier | V0.5.2 候选 |
| `continuous_observation.apply` | 高；连接现有事实流 | 中 | 修改正式 Current/Freshness | Panorama 写事务、Event 补偿、旧 Observation Policy 兼容同时存在 | 后续逐项接入 |

`engineering_event.record` 不能仅凭 `effectClass=event_append` 进入 V0.5.1。现有 Policy v0.1 没有把可追加的
Event Type、Actor/Producer、Authority、Outcome Label Strength 和 Subject 范围绑定进人工批准 Hash；直接接入
可能让“被允许写 Event”被误解为“被允许声明任意工程事实”。

## 3. V0.5.1 范围

### 3.1 必须交付

1. **只读 Head State Inspector**
   - 将 Event Chain 验证与 Head 状态分类分开；
   - 输出稳定状态码、当前 Head、唯一 Tail、Project/Stream/Epoch Binding 和可恢复原因；
   - Preview、Inspect 和 Validate 不分配 Policy Use，也不要求人工批准。
2. **严格恢复资格判断**
   - 只有 `head_missing` 和 `head_behind` 可以进入 Policy 执行；
   - `head_behind` 必须精确匹配 Chain 中较早的同 Project/Stream/Epoch Event；
   - `current` 返回 `no_recovery_needed`，不消耗 Use；
   - `head_ahead`、`head_mismatch`、`head_invalid`、`chain_invalid`、Fork、重复 Sequence、Hash mismatch、
     Project/Stream/Epoch mismatch 和 Redaction 歧义全部 fail closed。
3. **`event_head.recover` Policy Adapter**
   - 从正式 Panorama 读取 Project ID、Schema Version、Revision 和 Data Hash，不接受调用方自行声明；
   - Event Store 必须解析为项目自己的 `.panorama-work/event-store/v0.1`，拒绝绝对路径逃逸、符号链接和
     Project 外 Store；
   - Policy 必须为 `operation=event_head.recover`、`effectClass=deterministic_recovery`、
     `sourceBindingRule=not_applicable`，且 `recoveryRules` 保持全部 fail-closed 常量；
   - 在任何写入前调用 Approval Policy Core 分配 Use；
   - 恢复后先记录 Policy Audit Event，再写 Execution Receipt 并推进 Ledger；
   - 不把普通 Proposal/Studio Approval 当作 Delegated Policy。
4. **可恢复的 Adapter Transaction**
   - 保存有界、Project-local、带 `stateHash` 的恢复事务，默认位置为
     `.panorama-work/approval-policy-operations/v0.1/event-head-recover/<transaction-id>.json`；
   - `transactionId` 由 Policy ID/Hash 与 Input Hash 确定性派生，重试不得生成第二个 ID；
   - 至少记录 Policy ID/Hash、Use Number、Input Hash、Store Ref、Before Head、Expected Tail、Recovered Head、
     Output Hash、Receipt/Event Binding 和状态；
   - 支持 `prepared → allocated → effect_observed → finalized`，以及明确的 failed/conflict 状态；
   - 进程在 Head 已恢复但 Audit Event、Receipt 或 Ledger 尚未完成时，重试必须复用同一事务和 Use Number，
     不再次恢复、不重新分配 Use、不制造重复 Event；
   - State Hash、Observed Result 或 Resolution 被修改时 fail closed。
5. **Adapter Conformance Test Harness**
   - 将 Policy 预检、副作用前后故障注入、Event/Receipt/Ledger 对账、重试和 Store Validator 组合成后续
     Adapter 可复用的测试辅助层；
   - Harness 只服务本地测试，不演化成通用任务调度器或 Agent Runtime。
6. **CLI、合同和 Skill 路由**
   - 增加 Preview/Execute/Resume 的单一 CLI 路径；
   - 更新 Engineering Event、Approval Policy 和 SKILL 路由，明确 Policy 自动恢复与显式人工恢复的边界；
   - CLI 默认输出脱敏摘要；`--json` 输出机器可读状态和稳定错误码。

### 3.2 建议制品

最终文件名可在设计闭合时微调，但职责不得合并：

```text
schema/event-head-recovery-transaction.schema.v0.1.json
docs/event-head-policy-adapter-contract.md
scripts/event_head_inspector.py
scripts/event_head_policy_adapter.py
scripts/recover_event_head_with_policy.py

tests/test_v051_event_head_inspector.py

```

如果实现验证证明 Adapter Transaction 可以完全由现有 write-once Ledger/Receipt 无损恢复，则可以不增加新
Schema；但必须用故障注入证明 post-effect/pre-receipt 状态仍可确定性识别。不能为了少一个文件而丢失
Before/Expected/Observed Binding。

### 3.3 明确不做

- 不修改 Panorama Schema `0.1/0.2`；
- 不修改 Renderer `0.4.0`，不增加主视图；
- 不接入第二个 Delegated Policy Adapter；
- 不自动修复 Chain、Event、Epoch、Redaction Manifest 或 Project Binding；
- 不把 Head Recovery Event 当作 Approval、Acceptance、Gate Passed 或 Formal Finding；
- 不实现 Legacy Backfill、cat-sys 正式迁移、View IR、Exact Delta、Verified Delivery；

## 4. Head State 模型

Inspector 至少输出以下稳定状态：

| 状态 | 含义 | 自动 Policy Recovery |
| --- | --- | --- |
| `current` | Head 精确等于唯一 Chain Tail | 否；返回 `no_recovery_needed` |
| `head_missing` | Chain 完整且唯一，Head 文件缺失 | 是 |
| `head_behind` | Head 精确绑定同一 Chain 的较早 Event | 是 |
| `head_ahead` | Head Sequence 超过唯一 Tail | 否 |
| `head_mismatch` | Sequence 存在但 Event ID/Hash 不匹配，或身份字段不匹配 | 否 |
| `head_invalid` | Head JSON、Schema 或安全约束无效 | 否 |
| `chain_invalid` | Event Schema、Hash、Sequence、Previous Hash、Project/Stream/Epoch 任一无效 | 否 |
| `ambiguous` | 多 Tail、Fork、重复 Sequence 或 Redaction/Epoch 无法唯一解释 | 否 |
| `uninitialized` | 空 Store 且没有可验证 Project/Stream 身份 | 否 |

`not_detected` 不等于 `absent`。无法完整扫描、遇到符号链接、权限错误或输入超限时使用失败/unknown 类状态，
不得降级为 `head_missing`。

## 5. 执行与恢复协议

### 5.1 Preview

```text
Resolve exact project-local paths
→ Validate Panorama + Policy Store + Event Chain
→ Classify Head State
→ Verify Policy operation/scope/recoveryRules
→ Compute Target Tail + canonical Input Hash
→ Return Preview; no mutation, no Policy Use
```

Input Hash 绑定 Policy ID/Hash、Project/Schema/Data Binding、Event Store 相对路径、Stream/Epoch、唯一 Tail 的
Sequence/Event ID/Event Hash 和恢复规则。它不依赖显示文案或文件 mtime。

### 5.2 Execute

```text
Re-run Preview and compare exact Input Hash
→ Publish prepared Adapter Transaction
→ begin_execution() allocates one Use
→ bind Use Number to Adapter Transaction
→ revalidate recoverability under Event Store lock
→ atomically rebuild stream-head.json only
→ persist exact effect_observed result
→ complete_execution() writes Audit Event + Execution Receipt + Ledger
→ validate Event Store + Policy Store
→ finalize Adapter Transaction
```

不得在持有 Event Store Lock 时进入 Approval Policy Runtime。`complete_execution()` 会在 Policy Lock 内记录
Audit Event，因此 Adapter 必须使用固定锁顺序并避免 Event Lock ↔ Policy Lock 反向嵌套。

Execution Receipt 的 `outputHash` 定义为恢复结果对象的 canonical SHA-256，绑定 Recovered Head，而不是恢复后
继续追加的 Policy Audit Event 所形成的新 Stream Head；最终 Audit Event 由 Receipt 的 `eventBinding` 单独绑定。

### 5.3 Resume

- `prepared` 但没有 Ledger Pending：可安全废弃或重新 Preview，不消耗 Use；
- Ledger Pending 且 Head 仍为允许恢复状态：复用同一 Use 和 Input Hash 执行一次恢复；
- Ledger Pending 且 Head 已等于 Expected Tail：视为 effect 已发生，补写/复用 Audit Event、Receipt 和 Ledger；
- durable Receipt 存在但 Ledger 未推进：只调用现有 `recover_pending()`，不得创建新 Receipt；
- Adapter Transaction 未 finalized 但 Core Receipt/Ledger 已完成：对账后幂等 finalize；
- 任意第三状态、Hash 不匹配或无法证明同一事务：标记 conflict 并转人工，不 rebase。

## 6. 审批门禁

| 动作 | 门禁 |
| --- | --- |
| Inspect、Preview、Diff、Validate、Head State 分类 | 无人工审批 |
| 创建、修改、续期、替换 `event_head.recover` Policy | 准确 Policy Hash 的一次人工批准 |
| Policy 有效范围内的 missing/behind Head Recovery | 不逐次审批；必须生成 Receipt/Event |
| Head ahead、mismatch、invalid、Fork、歧义 | Adapter 停止；需要独立人工诊断/决策，不能用 Policy 绕过 |
| 修改 Event、Redaction、Epoch 或删除数据 | 不在本 Policy；需要独立治理批准 |
| 公开发布 `v0.5.1` | 已延迟；本规划不执行 Tag/Release/安装 |

Policy 激活不是本迭代实现的隐含授权。测试使用固定 fixture Policy；真实项目 Policy 仍必须展示完整 Scope、
Expiry、maxUses、Stop Conditions 和准确 64 位 Hash 后由用户批准。

## 8. 验证矩阵

### 8.1 允许路径

- 有效 Chain + `head_missing`；
- 有效 Chain + 精确 `head_behind`；
- Head 已是 current，Preview 返回 no-op 且不消耗 Use；
- 恢复后 Event Store 和 Policy Store 同时 valid；
- Audit Event、Execution Receipt、Use Number 和 Adapter Transaction 精确互相绑定。

### 8.2 拒绝路径

- Head ahead、同 Sequence 错 ID/Hash、Project/Stream/Epoch mismatch；
- Event Hash/Request Hash/Previous Hash mismatch；
- 重复 Sequence、Fork、多 Tail、Schema invalid、Redaction 歧义；
- Policy 过期、撤销、用尽、Hash mismatch、Operation/effectClass 不匹配；
- `recoveryRules` 缺失或任一安全常量被放宽；
- Panorama Project/Schema 与 Policy/Event Store 不匹配；
- Store 路径逃逸、绝对路径、符号链接或非 Project-local Store；
- Ledger 已有不相关 Pending Use，或 Adapter Transaction State Hash 被篡改。

### 8.3 故障与幂等

- Use 分配前失败不消耗 Use；
- Use 分配后失败消耗 Use并生成失败 Receipt，或保持明确 recovery-required；
- Head 已恢复后进程中断可以从 durable Transaction 继续；
- Audit Event 幂等命中不新增 Sequence；
- Receipt durable、Ledger 未推进只使用 Core Recovery；
- Finalize 重试不产生第二个 Use/Receipt/Event；
- 两个进程并发时最多一个进入真实副作用。

### 8.4 回归与容量证据

- V0.1/V0.2 Reference、V0.4 Evidence/Studio/Trace/Receipt、V0.5 Foundation 全部回归；
- Node URL sanitizer 与 Presentation Hash 门禁不回退；
- Python 3.10/3.12 CI 全绿；
- 使用 1,000 条最小 Event 的有效 Chain 记录一次恢复/校验耗时和内存，仅作为容量证据，不提前声明 SLO。

## 9. 内部冻结与未来发布条件

V0.5.1 作为内部基线必须满足：

1. 自动恢复仅接受 `head_missing|head_behind`，其他状态全部 fail closed；
2. Policy Scope、Project、Store、Rules、Use、Receipt 和 Audit Event 可端到端对账；
3. 所有 post-effect 故障都能确定性 resume 或明确 conflict；
4. success/no-op 不缺少 durable Event + Receipt，失败不冒充成功；
5. Recovery 本身不改变任何已有 Event、Panorama Data、Presentation 或业务文件；
6. 完整回归、Python 3.10/3.12 远程 CI 和 Skill quick validation 通过；
7. Milestone Audit 列出基线测试数、新增测试、已知限制和下一阶段的 No-Go 边界；
8. 内部 Commit 后工作树干净且远程 CI 绿色。

公开 Tag/Release/Installed Skill 不属于当前路线。如未来恢复单独发布，仍须独立发布评审与用户授权；本地或
远程门禁通过不能被描述为已经发布。
