### Privacy Root Detection Regression

Privacy Preflight 暴露出 exact directory-name set 无法识别带前缀的复合内容根；因此内容候选会错误落入 `PUBLIC_PROJECT_EVIDENCE`。修复使用唯一 canonical `_knowledge_root_name`：lowercase，统一 `_`、`.`、空格和 `-` 分隔，并只接受 exact knowledge concept 或以 `vault`、`wiki`、`knowledge`、`knowledge-base`、`kb` 结尾的分隔复合名称。

matcher 不使用 substring：`vault-tools`、`wiki-renderer`、`knowledge-graph`、`kb-client`、`myvault` 与 `knowledgebase-utils` 保持非 Knowledge Root。`_knowledge_base_hint` 与 `_knowledge_operational_parts` 共享同一 helper，消除 hint/index 分歧。

识别 Root 后继续执行既有严格规则：普通笔记和 `.obsidian` JSON 为 `PROJECT_CONTENT`；只有 Explicit Operational System Boundary + Operational Semantic + Safe Format 才能升级为 `PROJECT_OPERATIONAL_METADATA`。回归 fixture 覆盖 `sandbox-vault`，但生产逻辑没有该名称分支。AI-Wiki Privacy Preflight 与 Bare INIT 本轮均未重新运行。

## 3. Access Classes

实现五类访问边界：

- `PUBLIC_PROJECT_EVIDENCE`；
- `PROJECT_OPERATIONAL_METADATA`；
- `PROJECT_CONTENT`；
- `SECRET`；

Access Class 只决定可用读取路径，不代表 Fact Authority。Operational Metadata 仍需结合 Freshness、环境和 provenance 判断是否支持 Current 状态。

## 4. Secret / Project Content Safety

JSON、JSONL、YAML、TOML 与 generated Markdown Frontmatter 使用 bounded safe parser。password、token、secret、API/private key、credential、authorization、cookie、session 等键递归替换为 `***REDACTED***`；body、content、text、article、message、notes、description 等正文型字段从 Operational Facts 省略。

Inspector 拒绝绝对路径、root escape、符号链接、Secret-risk 文件、普通 Project Content 与不合格 Candidate。Structured 文件超过上限时 fail closed；generated Markdown 只提取 bounded prefix 中的状态行，不返回原始正文。

## 5. Runtime / Verification Observation

新增 `scripts/observe_project_runtime.py`，允许只读观察：

- Git HEAD、branch、dirty、状态条目数量与状态 Hash；
- project-relative 文件存在性；
- 顶层 Python dependency availability（不执行 import）；
- 指定 process name 与 scheduler name 状态；
- 项目 manifest 中 test command 的声明状态。

Process observation 不读取 PID 参数或环境。`safe=true` 只被视为项目声明：默认校验后返回 `requires_explicit_authorization / not_observed`，不会自动执行 Python、Node 或 native executable。用户明确授权准确命令后，Observer 才使用 `shell=false`、最小环境、超时、命令过滤和前后项目文件快照执行；结果明确记录 `networkIsolation=not_enforced`、`filesystemIsolation=not_enforced`、`projectWriteCheck=post_execution_metadata_check`，不再输出无法证明的 `networkUsed=false` 或 `secretValuesRead=false`。stdout/stderr 内容始终不返回。

## 6. INIT Materialization Contract

新增 `scripts/prepare_init_review.py` 与 `scripts/record_init_approval.py`，并将 `scripts/materialize_init.py` 改为双制品输入。PREPARE 接受完整 `draft-init-model.v0.1`，运行 Schema、Cross-reference、风险规则及派生 Review/Change 预校验；仅在全部通过后冻结 `prepared-init-review.v0.1`、计算 canonical `previewHash` 并生成固定章节 Review Markdown。

用户必须显式确认准确 Hash。Recorder 重新计算并核对 Hash，使用自身 clock 记录 `init-approval.v0.1`，固定 `approvalMethod=explicit_hash_confirmation` 与 `approvalTimeSource=approval_recorder_clock`，且已有 Approval 拒绝覆盖。Materializer 验证 `recomputed == prepared == approval`、比较 Source Snapshot、映射批准数据、运行 Validator、分类/聚类 Finding，并在最终 Schema/Cross-reference 校验后原子写出首版 JSON。Git Snapshot 继续过滤 `.panorama-work/`、Panorama lock/backup 与 `*.local.html`；真实 Source HEAD 或项目工作树变化仍会停止并要求重新 PREPARE/批准。

## 7. Initial Review / Change / UpdateBatch

确定性 ID 来自 Preview Hash prefix：

- `REV-INIT-*`：approved Panorama Update Review；requestedAt 使用 Preview T1，reviewedBy 使用真实用户，reviewedAt 使用 recorder 的 `approvalRecordedAt=T2`；approvalBinding 保存 approvedHash、approvalMethod 与 approvalTimeSource；
- `CHG-INIT-*-NN`：只映射已批准的语义 Change Intent，不按字段制造 Change；
- `UPD-INIT-*`：applied Initial UpdateBatch，revision `0→1`，关联 Review、Changes、Attention 与 Guidance option IDs，并写入 `meta.latestUpdateBatchId`。

Synthetic complex project 验证 Review、3 个语义 Change、UpdateBatch 与 Guidance 均被完整物化；相同模型与 Source Snapshot 重复运行得到相同 Data。

## 8. Finding Reconciliation

Materializer 只对 provisional Initial UpdateBatch 已存在后的实际 `validate_data` 输出分类：

- `PROJECT_GAP`；
- `PANORAMA_EVIDENCE_GAP`；
- `PANORAMA_MODEL_GAP`；
- `CONTROL_BLOCKER`；
- `INFORMATIONAL`。

Verification Finding 若存在相关、可用 Access Class 的 VERIFICATION Evidence，则为 `PANORAMA_EVIDENCE_GAP`；没有证据时为 `PROJECT_GAP`。明确 blocked Transition 为 `CONTROL_BLOCKER`。完整分类与 evidence paths 保存在 UpdateBatch extensions，不修改 Schema。写入 Reconciliation/Attention 后再次验证，最多进行 2 次稳定化；最终 Validator Finding 集合必须与 stored reconciliation 一致，最终 actionable High/Critical 必须与 Attention 一致，否则停止物化。

## 9. CONTROL Attention

只有 High/Critical、非 Informational Formal Finding 进入 Initial Attention，并按业务优先级、Finding Code 与 Class 聚类。核心回归构造 2 个 Module Verification High 与 1 个 blocked Transition High：Formal High = 3，CONTROL Attention = 2（Verification Evidence Mapping cluster + Transition Blocker），且保留全部 relatedEntities。

一致性 Gate 保证 actionable High/Critical > 0 时 Attention 不得为空，并逐项核对最终 Finding/Reconciliation/Attention，从而消除“Validator 有 High，但 CONTROL 显示没有关注事项”及保存中间旧 Finding 的状态。

## 10. Release Semantics

只有 `status=deployed` 的 Release 可以写入 `project.currentReleaseId`。planned/development/candidate/retired Release 仍可保留为实体，但若被误设为 current，PREPARE 必须失败，Materializer 也执行防御性断言并失败。实现不再设置 `currentReleaseId=null`，也不再记录 normalization；修正必须发生在批准前，并重新 PREPARE/批准。

Synthetic case 保留 candidate Release 实体但 `currentReleaseId=null`。另有回归验证 candidate-as-current 在 PREPARE 阶段失败。

## 15. Remaining Limitations

- Operational qualification 有意 fail closed；不常见的 operational 目录或文件名可能需要人工确认后才能读取。
- Structured metadata 超过 256 KiB 时拒绝解析；generated Markdown 只读取 64 KiB prefix。大规模 registry 需要未来设计分页/分片，而不是扩大无限读取。
- YAML/TOML Inspector 依赖 PyYAML；Python 3.10 还需要 tomli。脚本不会自行安装依赖。
- Test manifest 不能证明代码安全；默认只返回 `requires_explicit_authorization`。用户授权后仍没有 OS 级网络/文件系统 sandbox，只能诚实记录未隔离状态与项目内 metadata 事后检查。外部写入、网络和 Secret 读取无法被该检查证明或排除。
- Process/Scheduler 只报告指定名称的观察结果；`not_detected` 不能证明不存在。
- Evidence Inventory 与用户批准动作使用 Hash/结构校验而非公钥签名；其真实性仍依赖受控 Preview/Review 工作流。Recorder 证明的是本地记录时刻与显式 Hash 绑定，不是身份密码学证明。
- Materializer 只处理 revision 0、无既有 Review/Change/UpdateBatch 的正式 INIT；既有 Managed Panorama 必须继续走 Proposal/Apply。
