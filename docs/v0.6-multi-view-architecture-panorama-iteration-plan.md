# V0.6.0 Multi-View Architecture Panorama 迭代方案

状态：**WP0–WP6 Machine Gates Closed；WP7 Independent Human Visual Pending；尚未发布**

批准日期：2026-08-21

公开发布目标：`v0.6.0`

前置基线：已发布 `v0.5.0`；V0.5.1 `event_head.recover` 作为内部验证里程碑保留，不单独公开发布

后续版本调整：Dataset / Eval / Temporal RAG Export 由原定 V0.6 顺延到 V0.7

## 1. 决策结论

下一次公开发布不以单个治理 Adapter 为产品卖点，而以“基于源码与工程证据生成多种可交互架构视图”
作为完整用户价值闭环。V0.6.0 必须同时证明：

1. 能从源码、配置、作者模型、正式 Panorama 与 Engineering Event 中提取有来源绑定的工程关系；
2. 能从一套共享语义生成系统架构、模块/依赖、部署/运行、数据流、时序、生命周期与演进/风险视图；
3. 所有视图共享稳定身份、Evidence、Freshness、`asOf` 和 Unknown/Conflict 语义；
4. 支持缩放、搜索、聚焦、筛选、跨视图高亮、关系追踪、详情抽屉和稳定 Deep Link；
5. 候选制品经过语义、几何、浏览器、隐私、可访问性与 last-good 交付门禁；
6. Panorama 与 Archify 在同一批项目上完成对照验证，确认吸收了多图和交互方法但没有复制其事实模型；
7. 至少一条真实工程流程形成 Event → Sequence/Lifecycle/Evolution 投影，证明时序不是静态猜测。

版本策略固定为：

```text
V0.5.0 Released
  → V0.5.1 Internal Milestone（提交到开发分支、完整回归、无 Tag/Release/安装）
  → V0.6.0 Design Closure
  → Model/View IR + Source Extraction
  → Multi-View Compiler + Interactive Renderer
  → Event Capture + Verified Delivery + Proof Lab
  → V0.6.0 Release Review
  → 用户单独批准后 Public Release
  → V0.7 Dataset / Eval / Temporal RAG Export
```

## 2. 产品边界

### 2.1 V0.6.0 要解决的问题

- 用户无需先手工维护完整架构图，即可看到有证据边界的源码拓扑和架构候选；
- 同一实体可在不同视图中保持身份一致，并从任一节点追到来源、时间、风险和演进；
- Current、Target、Transition、Declared、Observed、Derived 与 Unknown 不再因切换图类型而混淆；
- 多图不是多份互相漂移的文档，而是同一工程事实的不同只读投影；
- 漂亮、可交互的 Single HTML 仍保持离线、本地优先和可审计交付。

### 2.2 明确不做

- 不增加第四个主导航；多图作为 `系统`、`演进` 内的 Guided View/Profile；
- 不建立五套互不兼容的 Diagram Schema，也不把布局坐标写入正式 Panorama；
- 不从目录名、文件相邻或 import 关系推断真实运行调用顺序；
- 不把 Mermaid、自然语言或 LLM 推断直接物化为正式 Current/Target；
- 不替换正式 Panorama Core，不把 View IR/Model IR 变成第三套事实源；
- 不直接复制 Archify Schema、Renderer 或视觉资产；
- 不在 V0.6.0 实现 Dataset/RAG/Eval Export、模型后训练、向量数据库、Agent 调度或云端协作；
- 不在本版本承诺所有语言、所有框架、完整 C4/Structurizr 无损导入或任意规模自动布局；
- 不把自动截图、几何检查或模型评分描述为人工视觉通过。

## 3. 目标架构

```text
Panorama Core -----------┐
Engineering Event -------┼──> Evidence-bound Model IR ──> View IR Compiler
Source Extractor Receipt ┤                                  ├─ architecture
Author Model + Loss -----┘                                  ├─ dependency/dataflow
                                                            ├─ deployment/runtime
                                                            ├─ sequence
                                                            └─ lifecycle/evolution/risk
                                                                       ↓
                                                              Layout / Viewer State
                                                                       ↓
                                                          Interactive Single HTML Candidate
                                                                       ↓
                                                     Validate → Receipt → last-good Delivery
```

### 3.1 Truth、Model、View、Layout 四层

1. **Truth Inputs**：正式 Panorama、Event Checkpoint、源码/配置观察、作者模型和各自的 Evidence Binding；
2. **Model IR**：对输入进行确定性归一化的只读工程关系模型，记录来源、权威、时间、冲突和 Loss；
3. **View IR**：按用途选择 Model IR 子图并增加阅读顺序，不产生新的工程事实；
4. **Layout/Viewer State**：坐标、缩放、主题、筛选和当前选择；不进入 Semantic Hash，不反写前三层。

Model IR 与 View IR 均是可删除、可重算的派生制品。它们必须绑定完整输入 Hash、Compiler Version、
`asOf`、Project、Schema、Source Revision/Digest 和 Event Checkpoint；任何输入漂移都会使旧视图 stale。

### 3.2 建议机器合同

Design Closure 阶段评审并冻结以下最小合同，文件名可以调整但职责不得混合：

```text
schema/source-topology-observation.schema.v0.1.json
schema/extraction-receipt.schema.v0.1.json
schema/panorama-model-ir.schema.v0.1.json
schema/panorama-view-ir.schema.v0.1.json
schema/panorama-view-delivery-receipt.schema.v0.1.json
docs/source-extraction-contract.md
docs/panorama-model-ir-contract.md
docs/panorama-view-ir-contract.md
docs/multi-view-renderer-contract.md
docs/verified-delivery-contract.md
```

关键字段至少覆盖：

- `entityRef`、`relationRef`、`eventRef` 与稳定 authored/derived ID；
- `sourceBinding`、`evidencePins[]`、`authority`、`confidence`、`freshness`、`factStatus`；
- `observed|declared|derived|unknown|conflict` 与 `current|target|transition|historical`；
- Relation Kind、Direction、Transport/Data Contract、resolved/unresolved/non-followable；
- `asOf`、Core Data Hash、Event Checkpoint Hash、Source Digest/Git Revision、Compiler Version；
- Semantic Hash 与 Layout Hash 分离；
- Extraction/Import 的 kept/dropped/approximated/blocked Loss Report；
- 人工视觉状态与自动质量状态分离。

## 4. 多视图能力范围

V0.6.0 使用一套共享 Model IR，提供以下 View Profile。Profile 是投影配置，不是新的事实 Schema。

| View Profile | 核心问题 | 允许来源 | 关键真实性约束 |
| --- | --- | --- | --- |
| System Context | 系统与外部参与者如何连接 | Core、配置、作者模型、明确接口 | 不从仓库目录臆造外部系统 |
| Module / Component | 责任单元与依赖如何组织 | Core Module、源码依赖、manifest、入口点 | 文件/目录不能自动等同正式 Module |
| Deployment / Runtime | 制品部署到哪里、当前观察到什么 | Deployment、Resource、配置、runtime observation | Declared 配置与 Observed Runtime 分层 |
| Dependency / Data Flow | 数据或依赖如何跨边界移动 | typed edge、schema、pipeline/config、receipt | import、调用、数据流不可互相扁平化 |
| Sequence | 一次交互或工程事务如何按序发生 | Event、trace、作者动态视图、经验证调用链 | 每条消息必须有顺序来源；不从邻接关系猜时间 |
| Lifecycle | 状态、失败、重试和终态如何转换 | 状态合同、Event、事务记录 | “可重试”文案不能替代真实回边 |
| Evolution / Risk | 架构如何变化、风险何时形成或消失 | Revision、Event、Finding、Freshness、Delta | Risk 作为覆盖层，不制造因果或 blast radius |

首个公开版本至少要有五类可用投影：

1. System Context / Module Architecture；
2. Dependency / Data Flow；
3. Deployment / Runtime；
4. Sequence；
5. Lifecycle / Evolution / Risk。

System Context 与 Module 可共用 Architecture Family，但必须能切换层级。大图采用层级展开、聚类、筛选和
Focus，不把完整仓库图强行塞入一个画布。Showcase 首屏建议不超过 12 个主节点；常规可读视图建议不超过
30 个节点；更大的语义集合通过层级/筛选进入，具体容量预算在 Design Closure 的基准测试后冻结。

## 5. 源码生成架构的可信路径

### 5.1 Extraction 分层

1. **Repository Inventory**：入口点、manifest、workspace、构建、部署与配置文件，只记录已读取的元数据；
2. **Language Adapter**：输出 typed dependency/call candidate，保留工具版本、解析状态和位置；
3. **Configuration Adapter**：容器、CI/CD、collector、route、queue、database 等声明事实；
4. **Author Model Adapter**：Structurizr/LikeC4 等作者模型，必须输出独立 Loss Report；
5. **Runtime/Event Adapter**：受信 trace、Receipt、Engineering Event，提供真实时序和运行观察；
6. **Architecture Grouping**：把源码元素归入责任单元时只生成 derived candidate，除非已有正式 Module 映射。

首版内置范围优先覆盖本项目真实需要：Python、JavaScript/TypeScript、JSON/YAML 配置、Git/非 Git Source
Binding。其他语言通过版本化 Adapter Receipt 接入，不在核心编译器中堆积启发式规则。

### 5.2 Evidence 与 Currentness

- 每个可见 Node/Edge/Message 必须关联 Evidence Pin，或明确标为 `derived|unknown` 并给出推导输入；
- Git 项目绑定精确 revision；非 Git 项目绑定完整 Source Content Digest 与覆盖状态；
- 旧 revision 的源码位置保持可读但不激活为 current deep link；
- 未解析 import、动态加载、反射、生成代码与外部私有依赖必须保留为 unresolved/unknown；
- Extractor 不能读取 Secret、外部私有正文或越出 Project Root；源码正文不进入 View/Receipt/Event；
- LLM 可以给出命名、分组或解释候选，但不能新增无证据关系，也不能提升 Authority。

### 5.3 Sequence 的额外门禁

Sequence 只接受以下顺序来源：

1. 实际 Engineering Event / runtime trace 的有序记录；
2. 明确作者定义的 dynamic/sequence model；
3. 具有可验证控制流和调用点的静态分析结果，但必须标为 `derived_possible_sequence`；
4. 用户明确提供并批准为 Target/Declared 的流程。

import graph、目录关系、服务依赖和自然语言描述不能单独生成 `observed_sequence`。同步/异步、返回、重试、
失败和跨边界机制必须来自证据；证据不足时保留 Unknown，不补齐“看起来合理”的箭头。

## 6. 交互与 UI 目标

### 6.1 信息架构

- 保留 `控制台 / 系统 / 演进` 三主视图；
- `系统` 内增加 View Switcher：Context、Module、Dependency/Data Flow、Deployment、Sequence；
- `演进` 内增加 Lifecycle、Exact Delta、Event Timeline、Risk/Freshness Overlay；
- `控制台` 继续承担 Currentness、Validation、Delivery Receipt 和关键门禁摘要；
- 所有 View 共享 Entity Drawer、Evidence Drawer、Search、Filter 与 Deep Link。

### 6.2 必须交付的交互

- Pan/Zoom、Fit、Mini-map 或等价定位能力；
- Search → Focus → Cross-highlight；
- Relation Trace、Route/Reach 和上下游过滤，但只遍历正式存在的边；
- Current/Target/Transition、Authority、Freshness、Risk、Evidence 完整性筛选；
- 同一实体跨 View 切换保持选择与稳定 ID；
- Entity/Relation/Event/Trace Deep Link；
- Light/Dark 保持语义颜色一致；
- 键盘可完成 View 切换、节点遍历、详情打开/关闭与主要筛选。

### 6.3 视觉和响应式门禁

- 采用克制、信息优先的现代 UI；颜色、线型和动效只表达已定义语义；
- 默认静态，只有用户主动开启演示/追踪时使用 motion；
- 对 1440×900、1600×1000、1920×1080、2048×1320 采集有界视口证据；
- Desktop 不允许横向/纵向文档溢出、边穿节点、标签遮挡关系或模糊共享走廊；
- 840px 以下使用分段面板，允许正常纵向滚动但不牺牲文字和触控目标；
- 自动门禁只输出 machine status；代表性制品必须有独立人工视觉 `accepted` 才能公开发布。

## 7. 实施工作包

### WP0 — V0.5.1 内部冻结与 V0.6 Design Closure

交付：

- 把 V0.5.1 标记为 `Internal Milestone Ready — Release Deferred`；
- 在开发分支形成可回溯提交并运行远程 Python 3.10/3.12 CI，不打公开 Tag；
- 登记 Model IR、Source Observation、Cross-view Identity、Sequence Evidence、Renderer Delivery Findings；
- 冻结 V0.6 Scope、兼容策略、容量分层、浏览器矩阵和人工视觉规则。

退出条件：V0.5.1 工作树干净且 CI 绿色；V0.6 未决语义均有明确处理规则。提交与远程 CI 触发仍需用户
另行授权，当前规划批准不自动执行这些动作。

### WP1 — Model IR / View IR Foundation

交付：Schema、Compiler、Validator、Semantic/Layout Hash、exact-ID registry、Freshness/`asOf` Binding。

退出条件：同一输入可重算；未知字段、重复 ID、悬空引用、输入漂移和不完整 Event Checkpoint 全部 fail
closed；纯布局变化不形成 semantic change。

### WP2 — Source Extraction Foundation

交付：Repository Inventory、Python/JS/TS/Config 最小 Adapter、Extraction Receipt、Loss Report、Evidence Pin。

退出条件：对受控项目关键 Gold Facts 全覆盖；type-only、unresolved、dynamic 和 declared/observed 边界不丢失；
不读取 Secret/外部私有正文，不越出项目根。

### WP3 — Multi-View Compiler

交付：Architecture、Dependency/Data Flow、Deployment、Sequence、Lifecycle/Evolution/Risk 编译器。

退出条件：所有视图共享 identity/evidence；0 条无来源关系；Sequence 消息顺序门禁通过；跨视图切换不改变
事实状态。

### WP4 — Interactive Renderer 0.5 Candidate

交付：View Switcher、层级展开、Search/Focus、Cross-highlight、Trace、Filters、Deep Link、统一 Drawer、主题与
键盘路径。

退出条件：语义/几何/安全/浏览器检查绿色；代表性视图在四个 Desktop viewport 与窄屏检查通过；无框架、
CDN、远程字体或默认网络请求。

### WP5 — Event Capture 与真实时序闭环

交付：先冻结 Event-specific Policy Scope，再接入一个有界 `engineering_event.record` 或等价 Capture Adapter；
选择 Panorama 自身一条治理/恢复流程形成 Event → Sequence → Lifecycle → Evolution 投影。

退出条件：Event Type、Actor/Producer、Authority、Label、Subject、Access Class 全部进入批准 Hash；Capture 失败
不伪造成功；真实流程可重放且无时间泄漏。

### WP6 — Verified Delivery 与 Proof Lab

交付：candidate/last-good 原子交付、Machine Receipt、viewport evidence、Panorama × Archify 同项目对照实验。

退出条件：失败候选不替换 last-good；自动与人工视觉状态分离；完整验证矩阵通过并可离线复核。

### WP7 — V0.6.0 Release Review

交付：Release Audit、最终版本/兼容说明、安装验证、公开示例和精确 Commit/Tag Binding。

退出条件：所有 Required Gate 绿色，无未处置 P0/P1；用户单独批准 Commit/Push/Tag/Release/安装动作。规划批准
不等同于外部发布批准。

## 8. 组合验证矩阵

### 8.1 必测项目组合

| 项目类别 | 建议对象 | 主要验证目标 | Panorama × Archify |
| --- | --- | --- | --- |
| Self-host | agent-project-panorama | Python/JS/Schema/治理事务、多视图与真实时序 | 是 |
| 长期非 Git 工程 | cat-sys | 轨迹、Revision/Freshness、Source Digest、Evolution/Risk | 是 |
| 图示工具 | Archify | 源码架构、五图能力、交互和视觉基准 | 是，互为被测对象与对照 |
| 常规源码型 OSS | 固定 revision 的中型项目 | 无作者模型时的源码架构质量 | 是 |
| 架构原生 OSS | LikeC4 / Structurizr 固定样本 | 作者模型导入、动态视图、Loss Report | 是或与原生输出三方对照 |
| 大型 Monorepo | Backstage 固定切片，再评审完整仓 | 分层、聚类、容量、渐进展开 | 代表性切片必测 |
| 声明与运行时项目 | OpenTelemetry Demo 固定 revision | declared dependency 与 observed trace 分离 | 特性声明前必测 |

所有公开 OSS 必须固定 commit、记录 license/access class，并保存最小 Gold Fact Manifest。环境阻塞可以如实
记录，但凡属于公开声明的核心能力不得以 `blocked` 代替通过。

### 8.2 必测质量维度

| 维度 | 公开发布硬门禁 |
| --- | --- |
| 事实准确性 | 关键 Gold Facts 100% 命中；全部 Gold Facts ≥95%，其余进入 Loss/Unknown；0 invented edge |
| Evidence | 每个可见 Node/Edge/Message 100% 有 Evidence Pin 或明确 derived/unknown binding |
| Cross-view Identity | 同一实体/关系/事件在所有视图使用相同稳定 ID；Deep Link 可恢复 |
| Freshness / asOf | Git/Data/Source/Event 任一漂移使旧视图 stale；未来事件不能泄漏到历史视图 |
| Sequence | 100% 消息具有顺序来源；同步/异步/返回/重试语义不由 Renderer 猜测 |
| Delta | 排序、主题、缩放、纯坐标不产生 semantic change；真实语义变更精确分类 |
| Geometry | 0 edge-through-node、0 hard overlap、0 ambiguous shared corridor；Showcase 0 warning |
| Interaction | Search/Focus/Filter/Trace/Cross-view/Deep Link 全部使用既有关系，不创造拓扑 |
| Accessibility | 主要流程键盘可达、焦点可见、Drawer/Dialog 焦点闭环、文本与触控下限满足合同 |
| Privacy/Security | 0 Secret/源码正文/外部私有正文泄漏；URL/path/symlink/size/depth 全部 fail closed |
| Determinism | 相同输入字节与版本产生相同 Model/View Semantic Hash 和 Receipt Binding |
| Compatibility | Schema 0.1/0.2、Renderer 0.4、V0.5 Event/Policy/Outbox 回归不退化 |
| Performance | Design Closure 冻结 Small/Medium/Large 数据集预算；全部项目在对应预算内通过 |
| Visual Review | 自动 viewport 全绿；代表性 light/dark 制品由人工明确 `accepted` |

Gold Facts 只覆盖选定验收范围，不把未抽取的完整仓事实当作错误缺失。任何“≥95%”必须同时满足关键事实
100% 和 Loss Report 完整，不能通过缩小分母或删除难例达标。

## 9. 审批门禁

| 动作 | 门禁 |
| --- | --- |
| Discovery、Extraction Preview、Model/View Compile、Diff、Validation | Read-only / Automatic Quality；不需人工审批 |
| Studio 草稿、布局、候选比较、Advisory Review | 不需人工审批 |
| 将 derived architecture 采纳为正式 Current/Target/Decision | 精确 Proposal Hash 的人工批准 |
| 启用或改变 Capture/Renderer/Delivery Policy | 精确 Policy Hash 的人工批准 |
| Policy 范围内确定性 Renderer Candidate / last-good Promote | Adapter 通过后免逐次审批；必须有 Receipt/Event |
| Hook 安装、外部导出、公开发布、Tag/Release/安装 | 独立人工批准 |
| Dataset/RAG/Eval/Post-training | V0.6.0 No-Go；进入 V0.7 前重新设计评审 |

## 10. 推荐执行顺序

1. 先完成 WP0，只闭合合同与内部基线，不启动公开发布；
2. WP1 与 WP2 形成最小可验证垂直切片：源码 → Model IR → 单个 Architecture View；
3. 再扩展 WP3，每增加一种 View 都先通过 source/evidence/cross-view identity 门禁；
4. WP4 在语义稳定后统一 UI，不用视觉重构掩盖数据合同缺口；
5. WP5 接入一条真实 Event Capture，为 Sequence/Lifecycle/Evolution 提供运行证据；
6. WP6 使用完整项目组合做 Panorama × Archify 对照、last-good 和人工视觉验收；
7. 只有全部公开发布硬门禁闭合后进入 WP7，并单独请求发布授权。

Single HTML；一个真实 Event Capture；Verified Delivery；多项目 Proof Lab。
