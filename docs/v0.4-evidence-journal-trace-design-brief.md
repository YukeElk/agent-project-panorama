# V0.4 Evidence、Journal 与 Trace Design Brief

状态：已批准进入分阶段实现
批准日期：2026-08-13
前置基线：V0.3 Architecture Studio 必须先独立冻结并通过现有回归

实现进度：P0A Evidence Inspector、P0B Studio Operations/Hash/Semantic Diff 与 P0C 可访问性基础已完成；P1、P2 尚未实现。

## 1. 目标

在不新增第四主视图、不引入通用 Agent 编排或评测平台的前提下，让 Panorama 更清楚地回答：

1. 某个事实从哪里来，属于 observed、declared、inferred、unknown 还是 conflict；
2. 当前证据是否仍与 Panorama、Git 和 Source Snapshot 一致；
3. Studio 中哪些操作改变架构语义，候选之间具体改变了什么；
4. Requirement、Decision、Module、WorkItem、Acceptance 与 Gate 之间有哪些真实追踪关系；
5. 外部验证结果如何以脱敏 Receipt 进入 Review/Proposal，而不直接制造 Gate 或批准事实。

## 2. 不变量与停止边界

- 保留 `CONTROL / SYSTEM / EVOLUTION` 三主视图。
- Evidence Inspector 放入 `SYSTEM → 架构来源`；Studio Journal/Diff 只扩展现有 Studio。
- Trace Route 从现有 Requirement、Module、Gate 或 Drawer 进入，不增加全局导航。
- Verification Receipt 是外部结果适配器，不是测试运行器、沙箱或自动选优系统。
- 浏览器只呈现或编辑隔离 Session；普通 Panorama 更新仍只修改 `project-panorama-data`。
- Agent 只能产生 advisory Risk Candidate，不能生成 Formal Finding、批准、验收、Gate 通过或部署事实。
- 任何正式治理变更仍使用 Proposal Hash、独立 Approval 与 Apply。
- 中文只用于显示；Schema Key、枚举、ID、Finding Code、JSON Pointer 和 CLI Flag 保持英文。

以下内容明确不在 V0.4 范围：Run 管理、Mission DAG 执行器、Agent 调度、工具租约、自动 Git Promote、
通用评测平台、自动总分选优、浏览器端批准以及恢复外部 Agent/测试环境/工具副作用的 Checkpoint。

## 3. 信息架构

### 3.1 SYSTEM → 架构来源 → Evidence Inspector

采用三段连续阅读结构：

1. 左侧事实列表：实体/JSON Path、Authority、Confidence、Observation Batch、记录时间；
2. 中央证据与冲突摘要：Evidence 字符串、Source Commit、Source Snapshot、相关 Batch；
3. 右侧来源详情：来源类型、访问限制、记录时间、绑定状态和可用 Reference。

首版不把 `evidence[]` 字符串伪装成可点击实体，也不从 Conflict 字符串构造不存在的“两侧证据”。

### 3.2 SYSTEM → 逻辑架构 → Architecture Studio

在现有画布和 Inspector 内增加：

- `Semantic / Layout` 双轨 Session Operations；
- Bridge 计算的完整 `semanticHash / layoutHash`；
- 候选字段级 Semantic Diff；
- 当前 stale、保存冲突和制品失效的具体原因；
- 每个字段是否影响 Semantic Hash 的持续提示。

该区域称为 `Session Operations`，不是不可篡改审计日志。V0.3 的 Undo/Redo 会恢复 Session 快照，
因此在独立不可变模型存在前不得称为 append-only Audit Journal。

### 3.3 CONTROL / Drawer → Trace Route

从 Requirement、Module、WorkItem、Acceptance 和 Gate 的既有入口打开追踪关系。Trace 只显示真实 ID
引用形成的边，不补全想象中的直接关系。Proposal 侧复用真实 JSON Patch、Affected Entities 和
Validation，不复制一套 Reconciliation Preview。

### 3.4 Verification Projection

在 Gate/Acceptance Drawer 中投影外部 Receipt 的验证时间线、Finding、原始证据 Reference 与隔离
声明。Receipt 导入入口属于工具/Bridge，不新增 Arena 页面。

## 4. P0A — Evidence Inspector 合同

### 4.1 现有数据映射

| UI 字段 | 数据来源 | 显示约束 |
| --- | --- | --- |
| Entity / Path | `factProvenance[].path` | Path 是正式值；实体类型可从注册表派生并标记 Derived |
| Authority | `authority` | 原样显示 observed/declared/inferred/unknown/conflict |
| Confidence | `confidence` | 只显示 high/medium/low/unknown，不换算百分比 |
| Evidence | `evidence[]` | 默认纯文本；只有与正式 Reference 明确匹配时才链接 |
| Source Commit | `sourceCommit` | null 显示 unknown，不推断当前 Commit |
| Observed At | `observedAt` | 表示记录时间，不等于当前仍有效 |
| Observation Batch | `observationBatchId` | 解析到 `observationBatches[]` 后显示批次摘要 |
| Source Snapshot | `sourceBinding/currentArchitectureSnapshots` | 显示已绑定值与覆盖时间 |

### 4.2 Freshness 语义

- 直接打开 Single HTML：只能显示 `recorded_as_of`、`historical` 或 `currentness_unknown`。
- 不得因为 HTML 中存在 `gitHead` 就标记 `current`。
- Bridge 模式：实时比较 Panorama Binding、Session Binding、实际 Git HEAD、Source Snapshot 和有界
  Source Content Digest，才可显示 `match/drift/uninitialized/incomplete`。
- `STALE` 必须带具体原因和检测时间；无法检测时使用 `not_observed`。

### 4.3 Conflict 语义

首版把 `observationBatches[].conflicts` 作为批次级 Conflict Summary，并关联该 Batch 的 provenance。
只有两侧来源、Authority、时间和范围均有正式绑定时才允许并列显示。否则显示：

`Needs Human Review — structured sides unavailable`

不得自动裁决、覆盖或降低冲突等级。

## 5. P0B — Studio Operations、Hash 与 Semantic Diff

### 5.1 双轨记录

- Semantic：节点/连线增删、名称、用途、职责、非职责、状态所有权、层级语义、假设、未知项、协议与
  数据语义变化。
- Layout：`x/y`、缩放、折叠、面板布局及纯视觉排序。
- 每条记录显示 `seq/at/actor/kind/target/before/after/affectsSemanticHash`。
- 页面只展示 Bridge 返回或从服务端 Session 读取的完整 Hash；离线显示 `not_computed_by_bridge`。

### 5.2 候选对齐与 Diff

节点对齐顺序：

1. 已有正式实体使用 `entityRef.type + entityRef.id`；
2. Session 草稿使用 `nodeId`；
3. 不以显示名称猜测同一实体。

连线优先使用正式 `entityRef`，草稿使用 `edgeId`；不得只按起终点合并语义不同的多条连线。

Semantic Diff 包含：

- added / removed / modified node 和 edge；
- responsibilities / nonResponsibilities；
- stateOwnership、purpose、rationale；
- assumptions / unknowns；
- protocol、communicationMode、flowDirection、dataSummary、reliabilitySummary；
- requirementIds、referenceIds 与正式实体引用。

明确排除：`x/y`、缩放、折叠、面板位置、纯视觉排序和操作时间戳。

### 5.3 stale 原因

在尚未版本化持久模型前，UI 可从当前状态派生以下原因，但不得静默写入正式 Panorama：

- `candidate_semantic_changed`
- `candidate_switched`
- `panorama_revision_changed`
- `data_hash_changed`
- `git_head_changed`
- `source_snapshot_changed`
- `source_content_changed`
- `session_cas_conflict`
- `coverage_incomplete`
- `formal_source_uninitialized`

多个原因必须同时保留；不得压缩成一个模糊的 `stale` 标签。

## 6. P0C — 可访问性基础

- 正文至少 13px，辅助文字至少 12px，主要触控目标至少 44×44 CSS px。
- 候选切换若使用 Tabs，必须实现 `tablist/tab/tabpanel`、方向键、Home/End 和焦点管理。
- 画布节点提供键盘选择与位置调整；纯布局移动不得改变 Semantic Hash。
- 所有 SVG 连线同时提供可聚焦/可阅读的文本数据流列表。
- Drawer/Dialog 打开后移动焦点，Tab 闭环，Esc 关闭，关闭后返回触发控件。
- 状态同时使用文字、图标和颜色；重要错误使用持续可见的 `role=alert`。
- 未实现完整 Tree 键盘模型前，不使用 `tree/treeitem` 角色。

本阶段只要求 WCAG 相关实现证据与键盘测试，不宣称完整 WCAG 认证。

## 7. P1 — Traceability 与 Gate Projection

### 7.1 允许的边

只从 Schema 中真实存在的 ID 引用建立边，例如：

- Requirement → Module / Acceptance / Reference / Review；
- Module → Requirement / Decision / WorkItem / Acceptance / Gate / Review；
- WorkItem → Requirement / Module / Decision / Acceptance / Reference；
- Acceptance → scoped entity / Evidence Reference / Review；
- Gate → scoped entity / Acceptance / Evidence Reference / Review；
- Release → Module / Deployment / Architecture Version；
- Deployment → Release / Architecture Version / Module Deployment。

不存在直接引用时可展示多跳 Route，但必须呈现中间实体，不能虚构直接边。

### 7.2 Gap 分类

- Validator 已返回的 Finding 使用正式 Finding Code。
- Renderer 自行派生的 uncovered/orphan/stale 只能叫 `Trace Gap Candidate`。
- `not_detected` 不等于 absent；引用数据不完整时状态为 unknown。

### 7.3 分层状态

状态是带证据的派生投影，不新增客户端可写布尔值：

- `change_ready`：当前 Proposal 与 Session/候选/基线一致，Formal Validation 有效且无保存冲突；
- `verified`：相关必需 Gate passed，且 Evidence Reference 完整；
- `accepted`：相关 Acceptance 已 accepted，verification passed 且 Evidence Reference 完整；
- `deployed_observed`：存在与 Release/Architecture 匹配的 active Deployment 观察。

条件不足时显示 `blocked` 或 `unknown` 及原因。V0.4 不使用语义不明确的 `integrated`。

## 8. P2 — Verification Receipt Adapter

Receipt 使用独立、版本化 JSON Schema，建议格式名：
`panorama-verification-receipt.v0.1`。

最小合同包括：

- project/source binding：Project ID、Commit、Source Snapshot、环境；
- producer：工具名称/版本、生成时间、Receipt Hash；
- verification：测试/检查 ID、状态、时间、Finding、Gate mapping；
- evidence：脱敏摘要、外部 Reference、大小与哈希；
- isolation：`networkIsolation/filesystemIsolation/processTreeIsolation`，允许
  `not_executed/not_enforced/unknown`；
- redaction：已移除字段、敏感等级和截断声明。

导入流程固定为：

`Schema Validate → Redaction Validate → Binding Check → Mapping Preview → Formal Validate → Proposal`

Receipt 默认只生成候选 `Reference(test_report)`、Evidence mapping 和 fact provenance。它不能直接：

- 将 Gate 设为 passed；
- 将 Acceptance 设为 accepted；
- 生成批准或 Waiver；
- 证明未执行的隔离能力；
- 自动选择最优 Agent/方案。

## 9. 交付顺序

1. M0：冻结 V0.3 基线，确保未提交 Studio 工作与 V0.4 分离。
2. M1：P0A Evidence Inspector，只读 Renderer 增量，不改 Panorama Schema。
3. M2：P0B Studio Operations/Hash/Semantic Diff。
4. M3：P0C 键盘、焦点、文本替代和响应式验收。
5. M4：P1 Trace Route 与 Gate/Acceptance/Proposal 投影。
6. M5：P2 Receipt 独立 Schema、适配器与 Preview；默认保持 experimental。

每个 Milestone 必须保持普通 Patch 只修改数据载荷；Renderer 更新继续通过显式 Renderer Upgrade。

## 10. 验收标准

### P0

- v0.1 无 provenance 数据时显示空态，不报错、不伪造来源。
- v0.2 可按 entity/path、Authority、Confidence、Batch 过滤和检查。
- 离线绝不把已记录 Commit 称为实时 current；Bridge Drift 显示具体原因。
- 字符串 Conflict 不生成虚构的左右证据。
- Studio 展示完整双 Hash、双轨操作与字段级 Diff；纯坐标移动不进入 Semantic Diff。
- 多 stale 原因可同时查看；CAS 冲突保留本地草稿。
- 候选、画布、连线列表、Drawer 和 Dialog 可仅用键盘完成主流程。

### P1

- 所有 Trace 边可回溯到实际 ID 字段；多跳路径显示中间实体。
- Trace Gap Candidate 与 Formal Finding 视觉和语义分离。
- `change_ready/verified/accepted/deployed_observed` 均能展示条件与证据，条件不足时不返回 true。
- Proposal Diff 与 `propose_update.py` 输出逐项一致。

### P2

- 无效、超限、路径逃逸、含敏感明文或 binding 不匹配的 Receipt 被拒绝。
- Receipt 中 `not_enforced/not_executed` 原样保留。
- 导入只生成 Preview/Proposal，不直接改变 Gate、Acceptance、Review 或 Approval。
- 多 Receipt 的时间线按稳定 ID/Hash 去重，并保留来源与脱敏声明。

### 全局回归

- `CONTROL / SYSTEM / EVOLUTION` 不变，不新增主视图。
- Reference JSON 与 HTML 数据一致，Presentation Hash 与目标 Renderer 一致。
- Schema、跨实体引用、风险规则、Proposal/Approval/Apply、备份和 Presentation 保护测试继续通过。
- 桌面、1024px 与 390px 视口无关键操作丢失；无相关 console error/warning。

### P0A 实现结果（2026-08-13）

- Renderer `0.4.0` 已在 `SYSTEM → 架构来源` 增加三栏 Evidence Inspector，并保留下方原架构基线差异。
- Schema 0.1 / 尚未观察的 Schema 0.2 显示显式空状态；未修改 Panorama Schema。
- 离线显示 `CURRENTNESS UNKNOWN`；顶部自动追踪标记改为“已记录”，不再把内嵌 HEAD 表述为当前。
- Bridge `/api/v1/context` 返回脱敏 `sourceFreshness`：实时状态、检测时间、原因、正式/实际绑定与
  Source Content Digest 摘要；不返回源码正文。
- Conflict 只呈现 Batch Summary，并固定显示人工复核边界；Evidence 只有精确匹配正式 Reference 才链接。

### P0B 实现结果（2026-08-13）

- Studio 显示 Bridge 权威完整 `semanticHash / layoutHash`；离线模式明确显示
  `not_computed_by_bridge`，不在浏览器伪造权威 Hash。
- Inspector 持续呈现 Semantic/Layout Session Operations，包含 seq、时间、actor、kind、target、
  before/after 与 `affectsSemanticHash`；操作继续保存在隔离 Session，不进入 Panorama payload。
- 候选比较升级为字段级 Semantic Diff：正式实体按 `entityRef.type + entityRef.id` 对齐，草稿按
  session-local ID 对齐；职责、状态所有权、假设/未知项、数据流协议与可靠性语义可见，坐标与操作时间排除。
- semantic edit、candidate switch、Revision/Data/Git/Source drift、CAS Conflict、coverage incomplete 与
  formal source uninitialized 可同时显示；仍不新增持久 stale reason 字段或修改 Panorama Schema。
- 候选新建、克隆和重命名改用原生 Dialog，不再依赖 `prompt()`；正式批准仍使用独立精确 Hash Dialog。

### P0C 实现结果（2026-08-13）

- 候选切换实现 `tablist/tab/tabpanel`、左右方向键、Home/End、roving tabindex 与焦点保持。
- 画布节点支持 `Alt + 方向键` 10px、`Shift + Alt + 方向键` 40px 布局移动；只追加
  `layout.move`，不会触发 Semantic artifact stale。
- SVG 连线对辅助技术隐藏，并为每条连线提供可聚焦的数据流文本列表与属性检查入口。
- Drawer 与原生 Dialog 实现焦点进入、Tab 闭环、Esc/取消关闭及触发控件焦点返回；关键冲突和
  Bridge 错误继续使用持续 `role=alert`。
- 840px 以下使用组件、画布、属性/检查分段面板，画布区域允许页面滚动，仅节点拖拽区域捕获手势。
- Studio 正文与辅助文字、主要触控目标按 P0C 尺寸基线调整；未使用 `tree/treeitem`，不宣称完整 WCAG 认证。

## 11. Schema 决策

P0 首版只派生 UI，不修改 Panorama Schema。以下扩展必须先依据
[`schema-findings.md`](schema-findings.md) 中 SF-24～SF-27 单独设计与批准：

- 显式 Fact Class 与结构化 Evidence Source；
- 富结构 Conflict 两侧与人工处置状态；
- 持久 stale reasons、不可变 Journal/Checkpoint；
- Verification Receipt 历史与 Gate mapping。

本 Design Brief 的批准不等于批准上述 Schema 重构，也不授权自动执行测试、调度 Agent、修改业务项目
或自动推进治理状态。
