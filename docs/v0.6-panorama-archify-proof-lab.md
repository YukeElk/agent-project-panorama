## 结论

这次同项目验证证明，当前 V0.6 已经具备“可验证的多视图投影与本地交付”，但还不具备对外宣称“从常见
源码项目生成完整架构全景”的条件。它的强项与 Archify 不重合：Panorama 在 Evidence Pin、Current/Target/
Unknown 边界、Information Gap、跨视图稳定身份和 Receipt/Policy/last-good 上更强；Archify 在源码阅读后的
编辑表达、Guided Views、边界/卡片组合、动效、导出和视觉完成度上明显更强。

因此后续设计不应复制 Archify 的事实层，而应吸收它的 View Composition：在同一 Model/Evidence 上允许多个
命名视图、同 profile 的 scope variant 和 Guided Story，保持每个可见关系仍由 Panorama Evidence 约束。

## 对 0.6 设计的直接调整

1. P0：新增 View Set / Guided View Contract，允许同一 profile 的 current/target/transition/historical variant，
   Renderer 顶层是命名 Story/View，而不只是固定六个 profile tab；
2. P0：为“基于源码生成架构”增加 Language Coverage Gate。未知/未支持语言必须在生成空 Model 前阻断公开能力
   声明；
3. P1：实现 Java Adapter，或先增加一个固定 Python/TypeScript 公开项目作为第二个 source-generated 硬门禁；
   Spring PetClinic 继续保留为 Java 能力门禁，不能删除难例；
4. P1：建立 source_element → authored Module 的显式 Mapping/Promotion Proposal；在没有人工/规则批准的 mapping
   前，Dependency View 可以显示源码拓扑，但 Module Architecture 不得自动吸收文件；
5. P1：吸收 Archify 的边界、证据卡、Guided Story、视觉层级与导出体验，但继续复用 Panorama Model/Evidence，
   不建立第二套事实 JSON；
6. 发布前：对最终 Commit 重跑受控 + 至少一个受支持公开项目，随后由独立人工接受精确 V0.6 Artifact Hash。
