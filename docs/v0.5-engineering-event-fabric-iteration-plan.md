## 1. 决策摘要

下一阶段不应把 Panorama 扩展成通用 Agent 平台，而应增加一个与正式 Panorama 状态分离的、
本地优先的工程事件层：

```text
项目事实 / Studio / Proposal / Approval / Receipt
                    ↓ 现有受治理事务
         ┌──────────┴──────────┐
         ↓                     ↓
正式 Panorama Core State   Engineering Event Fabric
         └──────────┬──────────┘
                    ↓ 精确 ID、只读、可重算
             Panorama View IR
             ↙              ↘
      Single HTML Renderer   Verified Export + Receipt
                                      ↓
                            RAG / Eval / Post-training
```

推荐坚持以下产品分工：

- Panorama Core：维护 Current / Target / Transition、正式治理状态、Evidence 与 Trace；
- Event Fabric：记录这些状态形成、失效、验证和被批准的过程；
- View IR：从 Core + Event Checkpoint 确定性编译出的只读投影，不是第三套事实源；
- Verified Delivery：校验派生视图、保留最后一个合格制品，并生成机器可读交付回执；
- Export Adapter：生成外部消费者可用的数据包；
- 外部系统：负责向量索引、评测执行、训练、Agent 调度与在线服务。

Panorama 不执行训练、不托管向量数据库、不运行通用 Eval、不调度 Agent，也不自动选择或应用方案。
Archify 不作为 Panorama 的 Renderer 替代品；只吸收其可验证投影、精确差分和证明语料方法。

## 2. 为什么现在迭代

V0.4 已完成 Evidence Inspector、Studio Operations、Trace Projection 与 Verification Receipt Adapter，
但现有记录仍分散在四条不同语义的流中：

1. `factProvenance / observationBatches`：事实观察与自动 Current 物化；
2. `changes / reviews / updateBatches`：人工治理变更；
3. Studio Semantic/Layout Operations：隔离设计会话；
4. Verification Receipt：外部验证声明与证据映射。

这些结构可以解释局部历史，但不能形成统一、不可变、可导出、可按时间重放的工程事件流。

cat-sys 提供了一个高密度真实样本：

- 64 条人工轨迹记录；
- 14 个 Proposal 文件、13 个唯一 Proposal Hash；
- 两次精确用户批准与两次正式 Apply；
- Proposal 从 4 个 High Finding 收敛到 0；
- 一个生产门禁 Proposal 先因 3 个 Schema Error 失败，再修正并最终批准；
- 多次保留“工具存在 ≠ 已运行”“安装 ≠ Running”“Schema Pass ≠ Runtime Pass”；
- 正式 Panorama 已到 Revision 2，但两个核心叙事报告仍停留在 Revision 1，形成可解释的 Freshness Drift；
- 项目不是 Git 仓库，现有 Commit Binding 无法覆盖其演进。

这说明下一阶段最有价值的问题不是增加一条 UI 时间线，而是建立稳定的事件语义、完整性、
时间边界、来源绑定、保留策略与导出合同。

## 3. 目标与非目标

### 3.1 目标

V0.5 需要让 Panorama 能够回答：

1. 某个事实、风险、Proposal、Receipt 或治理状态是怎样形成的；
2. 哪些事件只是观察或建议，哪些获得了正式验证、精确批准或真实运行结果；
3. 某个时间点之前 Agent 当时能够看到什么，之后发生了什么；
4. 哪个事件导致 Proposal、Receipt、Session 或 Evidence 失效；
5. 非 Git 项目如何通过完整 Source Content Digest 绑定事实；
6. 如何在不暴露源码、Secret、日志正文或外部私有数据的前提下导出事件；
7. 如何把轨迹安全地构造成 RAG Bundle、Eval Episode 或 Dataset Package。

### 3.2 非目标

V0.5/V0.6 不提供：

- 通用 Agent Runtime、Mission DAG、工具租约或多 Agent 调度；
- 在线向量数据库、云端事件总线或多租户后端；
- 自动执行任意测试、训练任务、模型评测或数据标注；
- 自动总分选优、自动批准、自动推进 Gate/Acceptance；
- 隐藏思维链、Prompt 全量录制或 Secret/源码正文采集；
- 外部工具副作用、进程、网络或测试环境恢复；
- 业务 Git 分支自动提交或自动 Git Promote；
- 五套独立 Diagram Schema、Mermaid 自动导入、WYSIWYG、通用自动布局或品牌资源抓取；
- 默认动画、展示型主题扩张，或以截图/视觉检查替代语义与人工评审。

## 4. 核心设计原则

### 4.1 状态与事件分离

- 正式 Single HTML 继续是当前工程认知状态的物化视图；
- Event Fabric 是独立 Sidecar，不直接进入 `project-panorama-data`；
- V0.5 不把 Event Store 设为 Panorama 的唯一事实源，不做一次性 Event Sourcing 重构；
- 只有现有合法事务成功后，事件才能记录该事务的结果；
- Event Store 不得绕过 Proposal、Approval、Apply 或 Observation Policy。

### 4.2 不可变不等于真实

- Hash Chain 只证明事件未被静默改写，不证明内容真实；
- 每个事件继续保存 Authority、Confidence、Evidence 与 Freshness；
- Agent 生成的判断只能是 Candidate/Advisory；
- Formal Finding 仍只来自实际 Validator；
- Approval、Acceptance、Gate、Deployment 等事实仍遵守现有治理合同。

### 4.3 记录结构化结果，不记录隐藏推理

- 保存结构化动作、输入绑定、差异、证据、结果和失败原因；
- 不保存隐藏思维链；
- 可保存对用户有意义且已显示的简短 rationale，但必须标明 `declared` 或 `advisory`；
- 原始 stdout/stderr、请求正文、模型回答正文、源码和凭据默认不进入事件。

### 4.4 先 Sidecar，后投影，最后导出

1. 先证明事件可安全生成、校验、去重和恢复；
2. 再投影到现有 EVOLUTION / Evidence / Drawer，不新增主视图；
3. 最后提供脱敏导出，不在 Panorama 内实现消费平台。

### 4.5 Truth、Projection 与 Viewer State 三层隔离

- Core/Event 保存工程语义和时间事实；View IR 只保存一次可重算的阅读投影；
- View IR 必须绑定 Core Data Hash、Event Checkpoint Hash、`asOf`、Compiler Version 与 Renderer Version；
- 搜索、聚焦、Trace Route、章节播放、主题、缩放等 Viewer State 不写回 Core/Event/View IR；
- Presentation Profile 不得改变实体/关系 ID、拓扑、Authority、Freshness、风险或治理状态；
- 派生制品失败只能阻止本次交付，不能回滚或污染已经成功的正式治理事务。

## 5. 建议发布路线

### 5.1 V0.4.1 — Readiness 与升级断层修复

目标：先解决真实使用摩擦，不改变 Panorama Schema。

交付范围：

- 增加 Runtime Preflight：报告可用 Python、`jsonschema`、PyYAML、Git、Node 与 Schema/Renderer 兼容性；
- Windows 上 `python` 被 Store Alias 占用时，明确提示使用 `py` 或 Codex bundled runtime；不得自动安装依赖；
- 在 Skill 工作流中增加“极简项目快速复杂化”检测：实现根、测试、部署或多模块证据显著增加时，
  触发 Complex Upgrade Review，而不是继续把旧骨架当 Current；
- 明确 `Validator valid ≠ Source current`，在 Schema 0.1 的 INSPECT 中强化 Reality Drift 提示；
- 为 Narrative Reference 增加只读 Freshness Audit 报告，不修改 Reference Schema；
- 把现有 Verification Receipt、Proposal Wrapper、独立 Approval 的推荐调用方式收敛到单一路径。

验收：

- 无依赖环境给出可执行、非误导的诊断；
- 不调用网络、不安装依赖、不读取 Secret；
- 极简项目复杂化后不会继续走新建极简 INIT；
- V0.1/V0.2 Reference Project 和 V0.4 Renderer 回归全部通过。

### 5.2 V0.5.0 — Engineering Event Foundation

目标：建立独立、版本化、不可变的本地工程事件合同与存储，并随同发布已闭合的 Approval Policy Core 和
显式 opt-in Proposal/Apply Governance Outbox。这三项共同构成 V0.5.0 候选范围；其他 Operation Adapter、
Projection、Renderer 改版与 Export 不进入该版本。

新增制品建议：

```text
schema/engineering-event.schema.v0.1.json
docs/engineering-event-contract.md
scripts/event_store.py
scripts/record_engineering_event.py
scripts/validate_event_store.py
tests/test_v050_event_schema.py
tests/test_v050_event_store.py
```

默认存储：

```text
.panorama-work/event-store/v0.1/events/<event-id>.json
.panorama-work/event-store/v0.1/checkpoints/<checkpoint-id>.json
.panorama-work/event-outbox/<transaction-id>.json
```

选择“一事件一文件”而不是直接追加单一 JSONL：

- 更适合 Windows 原子替换和故障恢复；
- 单个事件可独立 Schema Validate 和内容寻址；
- 避免进程中断产生半行 JSON；
- 导出时再确定性生成 NDJSON。

每个项目使用单一顺序流和同一独占锁。Checkpoint 是加速索引，不替代事件 Hash Chain。

#### 5.2.2 首批事件类型

Observation：

- `source.triggered`
- `source.drift_detected`
- `observation.started`
- `observation.applied`
- `observation.failed`
- `conflict.detected`

Governance：

- `proposal.created`
- `proposal.superseded`
- `proposal.rejected`
- `approval.recorded`
- `change.applied`
- `change.apply_failed`

Studio：

- `studio.session_created`
- `studio.candidate_checkpointed`
- `studio.validation_completed`
- `studio.proposal_frozen`

Verification：

- `verification.receipt_previewed`
- `verification.receipt_rejected`
- `verification.receipt_imported`
- `validation.completed`

Risk/Freshness：

- `risk.candidate_raised`
- `risk.state_observed`
- `reference.stale_detected`
- `artifact.invalidated`

默认不把每次拖拽、布局移动或键入变成全局工程事件。完整 Studio Operations 继续留在 Session；
Event Fabric 只记录可绑定的语义 Checkpoint、Validation、Proposal 与正式化结果。

#### 5.2.3 事务与故障恢复

采用本地 Transactional Outbox：

1. 在现有事务锁内生成 pending Outbox，绑定 Base 与预期 Result Hash；
2. 执行原有 Observation/Apply/Import/Session 事务；
3. 重新读取并核对 Result Binding；
4. 原子写入最终不可变事件；
5. 将 Outbox 标记为 finalized；
6. 崩溃恢复时按 Base/Result Hash 判断 finalize、abandon 或 conflict，不猜测结果。

Event 记录失败不得把未完成治理动作描述为成功。是否让事件持久化失败阻断正式 Apply，必须在 M0
合同评审中明确；推荐治理 Apply 使用 fail-closed，普通只读 Trigger 使用可补偿模式。

### 5.3 V0.5.1 — Capture Adapters 与时序投影

目标：把现有四条记录流适配为统一事件，但不改变其各自权威语义。

适配顺序：

1. `propose_update / approval / apply_patch`；
2. `continuous_observation`；
3. Verification Receipt Adapter；
4. Architecture Studio Checkpoint/Validation/Proposal；
5. INIT Preview/Approval/Materialization；
6. Legacy Narrative Trajectory Backfill。

需要新增的标准 Receipt Profile：

- test/build；
- browser QA；
- migration/schema-head；
- provider/API；
- runtime/deployment；
- backup/restore；
- benchmark/golden-set；
- governed deletion/privacy lifecycle。

Receipt Profile 只是生产方/映射规范，不授权 Panorama 执行对应命令。

Renderer 只在现有位置增加投影：

- EVOLUTION：按事件显示变更、验证、失效和结果；
- Evidence Inspector：显示事件的 Authority、Binding、Freshness 与 Evidence；
- Proposal/Receipt Drawer：显示 supersedes/causation 链；
- 不增加第四主视图，不提供任务队列或 Agent 运行控制。

### 5.4 V0.5.2 — cat-sys Pilot 与兼容迁移

目标：用真实纵向案例验证事件合同，而不是把 cat-sys 特例写死进生产代码。

Legacy Backfill 必须：

- 将 64 条 Markdown 行导入为 `backfilled=true` 的 Narrative Event；
- 保留 `timePrecision=date`，不使用文件 mtime 冒充发生时间；
- 将 14 个 Proposal 文件识别为 13 个唯一语义版本；
- 将两次用户批准与两次 Apply 绑定到对应 Proposal Hash 和 Revision；
- 保留首个无效生产门禁 Proposal及其 3 个 Schema Error；
- 将 Proposal v1→v7、production gate v1→v6 建立 supersession 链；
- 将 Revision 1 叙事报告与 Revision 2 Panorama 的差异标为 historical/stale，不覆盖任何一侧；
- 对仓库外 Receipt/Backup 只保存 External Private Reference、Hash/availability 声明，不读取内容；
- 对非 Git 项目使用完整 Source Content Digest，覆盖不完整时不得称为 current。

兼容策略：

- Schema 0.1/0.2 Panorama 均可关联 Event Sidecar；
- 不要求把现有 Panorama Schema 立即迁移为 0.3；
- 没有 Sidecar 时 V0.4 行为保持不变；
- Legacy Backfill 是显式命令，默认 Preview，不自动写入；
- Backfill 结果不能升级原始证据 Authority 或标签强度。

### 5.5 V0.5.3 — Verified Projection、Exact Delta 与 Proof Lab

目标：在不扩张正式 Panorama Schema 和三主视图的前提下，建立 Core/Event 到阅读制品的
确定性编译、验证和证明链。

建议新增制品：

```text
schema/panorama-view-ir.schema.v0.1.json
docs/panorama-view-ir-contract.md
docs/verified-delivery-contract.md
scripts/compile_view_ir.py
scripts/compare_view_ir.py
scripts/validate_view_ir.py
scripts/deliver_verified_projection.py
tests/proof-lab/manifest.json
tests/test_v053_view_ir.py
tests/test_v053_exact_delta.py
tests/test_v053_verified_delivery.py
```

View IR 合同：

- 只从 Schema-valid Core State 和完整 Event Checkpoint 编译；不得从页面文案或显示名称反推事实；
- 使用正式 `entityRef.type + entityRef.id`；关系使用 authored ID，缺失时由字段所有者和精确 JSON Pointer
  确定性派生，不用数组位置、标签或坐标充当身份；
- `viewType` 只允许现有用途的有界投影，例如 `architecture`、`evolution`、`trace`、`evidence`、
  `event_timeline`；它们共享一套正式语义，不演化成五套事实 Schema；
- 同一 Core/Event/`asOf`/Compiler 输入生成相同 Semantic Hash；坐标和主题不进入该 Hash；
- `inspection` 与未来可选的 `share` Profile 只约束密度、视觉验收与脱敏强度，不改变语义；
- View IR 是缓存或交付输入，可随时重建，禁止反向 Apply 到正式 Panorama。

Exact Delta 合同：

- 只按稳定 ID 对齐实体、关系和事件；
- 分开报告 added / removed / semantic_changed / moved / rerouted / evidence_changed /
  freshness_changed / presentation_changed；
- 格式、对象键顺序、数组重排和纯 Viewer State 不得形成语义变化；
- Delta 只陈述被比较快照中的精确事实，不推断 blast radius、risk、merge safety 或 deployment impact；
- Before、Delta、After 及其输入绑定同时进入 Machine Receipt。

Verified Delivery 合同：

1. Schema Validate；
2. Referential/Binding Validate；
3. Semantic Invariant Validate；
4. Geometry/Composition Validate；
5. HTML/SVG/Security Validate；
6. 有界 Viewport Evidence Capture（可用时）；
7. 同目录 Candidate 检查通过后原子替换；失败保留 last-good；
8. 输出单一机器可读 Receipt，包含稳定 rule code、subject、measured evidence、supported fixes、
   artifact hash、source bindings 与 `visualReview=pending|accepted|rejected|skipped`。

`visualReview=pending` 不得称为视觉通过；自动检查只证明可测量条件，人工审阅仍是独立事实。

Proof Lab 首批必须覆盖：

1. Schema 0.1、无 Git、Source Digest 完整；
2. Schema 0.2、Git revision current；
3. Git/Source/Data/Event 任一漂移导致旧 Projection stale；
4. Studio 多候选 exact-ID Delta，纯布局变化与语义变化分离；
5. Receipt passed 但 Gate 未批准；
6. Invalid Proposal 被保留并产生失败回执；
7. cat-sys Legacy Backfill、Supersession 与 Revision 1/2 Freshness Conflict；
8. Redaction/Tombstone 后 Hash Chain 与 Export Manifest 可解释。

每个场景提交最小输入、预期 View IR/Delta、机器 Receipt 与可打开的 Single HTML；浏览器截图是
人工复核证据，不作为跨平台像素级 Golden Truth。

### 5.6 V0.6 — Dataset、Eval 与 Temporal RAG Export

V0.6 只提供版本化、脱敏的导出适配器，不实现消费平台。

建议制品：

```text
panorama-event-export.v0.1
panorama-rag-bundle.v0.1
panorama-eval-episode.v0.1
panorama-dataset-manifest.v0.1
```

#### 5.6.1 Temporal RAG Bundle

必须支持：

- `asOf` 时间/Revision 截断，禁止未来事件进入上下文；
- Project、Entity、Event Type、Authority、Freshness 与 Evidence 过滤；
- 实体/Trace 边与事件摘要联合导出；
- Current 和 Historical 明确分区；
- 不导出 Secret、源码正文、外部私有内容或隐藏思维链；
- Bundle 只包含可索引数据，不内置向量数据库。

#### 5.6.2 Eval Episode

每个 Episode 保存：

- Cutoff 前可见的事件与状态；
- Task、允许的工具/证据边界；
- 预期不变量与可观察结果；
- Cutoff 后 outcome 只进入评分侧，不进入模型上下文；
- Project-level split，禁止同项目未来版本跨 Train/Test 泄漏。

cat-sys 首批 Eval Case：

1. Schema Pass 不得外推 Runtime Pass；
2. Installed 不得外推 Running；
3. Runtime Receipt 已通过但 Gate 未批准；
4. Evidence 变化导致旧 Proposal Hash 失效；
5. 执行器超时不得冒充产品测试失败；
6. SQLite 结果不得外推 PostgreSQL RLS；
7. 恢复演练先失败后修复；
8. 不可变 Evidence 与受治理删除并存；
9. Narrative Revision 1 与 Formal Revision 2 Freshness 冲突；
10. Invalid Proposal 必须保留而不能静默改写为成功。

#### 5.6.3 Dataset Manifest 与标签强度

不使用单一“正确/错误”布尔值。建议分层：

- Tier A — `governed_outcome`：精确人工批准、Apply 与 Result Binding 完整；
- Tier B — `formally_validated`：Formal Validator 或匹配绑定的 Receipt；
- Tier C — `observed`：只读观察或受限执行结果，隔离声明完整；
- Tier D — `declared_or_narrative`：文档、人工轨迹或 Legacy Backfill；
- Tier U — `unknown_or_conflict`：证据不足或来源冲突。

Export 必须保存原始 Authority，Tier 只作为消费侧派生，不覆盖事实语义。

Post-training Export 只有在以下条件全部满足后才进入正式范围：

- 多项目样本，不以 cat-sys 单项目外推；
- 明确数据所有权、许可、保留与删除策略；
- Project-level/temporal leakage test 通过；
- 失败、拒绝、no-op 和 unknown 样本被保留；
- Agent Candidate 不被自动当作 Gold Label；
- 用户显式授权准确 Export Scope。

## 6. Schema Findings 与批准门禁

以下 Finding 已在 `schema-findings.md` 记录并完成 V0.5 Sidecar 设计评审：

- SF-28：缺少跨 Observation/Governance/Studio/Receipt 的统一事件 Envelope；
- SF-29：缺少 Proposal Supersession、Causation 与 Artifact Invalidation 关系；
- SF-30：非 Git 项目缺少可复用的完整 Source Content Digest Binding；
- SF-31：Append-only 与保留、导出、隐私删除之间缺少正式策略；
- SF-32：Event 与 Panorama State 双写缺少 Outbox/Recovery 合同；
- SF-33：Dataset Label Strength、Usage Authorization 与 Leakage Boundary 缺少正式模型；
- SF-34：Core/Event 到只读 View IR 的 Binding、版本与可重算合同缺失；
- SF-35：关系稳定身份与 exact-ID Delta 分类缺少统一合同；
- SF-36：派生制品的机器 Receipt、last-good、视觉证据状态与原子交付合同缺失；
- SF-37：审批粒度按机械步骤切分，缺少单 Operation、可撤销、可审计的 Delegated Policy Envelope。

同时复用而不重复发明：

- SF-24：显式 Fact Class 与结构化 Evidence Source；补充 Git revision / 完整 Source Digest Pin，
  只有精确验证时才能激活源码位置；
- SF-25：富结构 Conflict；
- SF-26：持久 stale reasons、Journal 与 Checkpoint；
- SF-27：Verification Receipt 多次运行历史。

设计闭合批准 SF-28～SF-37 的独立 Sidecar 机器合同与交付顺序，不批准 Panorama Schema `0.1/0.2`
字段迁移，也不自动启用 Policy Runtime、Adapter、Export 或外部执行。

## 7. 安全、隐私与保留策略

### 7.1 默认不记录

- Secret、Credential、环境变量值、Cookie、Authorization Header；
- 项目源码、知识正文、测试日志正文、模型回答正文；
- 外部私有文件内容；
- 隐藏思维链；
- 浏览器 Session、用户输入正文或医疗/个人业务数据。

### 7.2 完整性与删除

- Append-only 不能凌驾于合法删除和用户撤回授权；
- Event Store 需要 Project-local retention policy；
- 导出包必须有独立 Manifest、来源范围、生成时间和删除/撤回标识；
- 删除事件不得伪装为原事件从未存在；但敏感载荷必须允许真正移除或加密密钥销毁；
- Hash Chain 发生合法删改时，使用版本化 Tombstone/Redaction Manifest 解释断链，不伪造连续性。

### 7.3 Prompt Injection

- 事件中的 Evidence 和 Narrative 一律视为不受信数据；
- RAG Bundle 不得把检索内容中的命令当作 Skill 指令；
- Event/Export Schema 必须区分 data 与 instruction；
- 外部消费者需要明确的 untrusted-content boundary；
- Share/Export 制品默认移除本机绝对路径、私有仓库 URL、未授权 Evidence Link 与 Viewer 临时状态；
- Deep Link 只允许稳定 ID、关系 ID、事件 ID、Trace ID 与 `asOf`，不得承载源码、Prompt、Token 或凭据；
- 生成 HTML 默认自包含且不主动取网；任何外部资源能力均不进入 V0.5 范围。

## 8. 验收与质量门禁

### 8.1 Event Store

- Schema-valid 事件可确定性计算 ID/Hash；
- 重复事件幂等，不重复计数；
- 旧事件不可覆盖；
- 任意内容篡改可被检测；
- Sequence、Previous Hash、Project Binding 与 Subject Ref 完整；
- 并发写入、进程中断和 Outbox 恢复有确定性测试；
- Presentation Hash 与正式 Panorama JSON 在只记录事件时保持不变。

### 8.2 语义边界

- Observation 不能生成 Approval；
- Receipt passed 不能直接生成 Gate passed；
- Agent Review 不能生成 Formal Finding；
- Layout Operation 不进入工程语义事件；
- Candidate/Backfill 不升级为 confirmed/accepted；
- `not_detected`、`not_run`、`not_enforced` 和 `unknown` 原样保存。

### 8.3 数据质量

- 每个 Event 有稳定 ID、类型、记录时间、Project Binding、Authority 与 Privacy；
- 精确时间缺失时明确 Time Precision；
- Source 覆盖不完整时 Freshness 不得为 current；
- 同一 Proposal Hash 去重，不同 Hash 不覆盖；
- Narrative 与 Formal State 冲突被保留并可按 `asOf` 解释；
- Dataset Export 通过 Secret scan、路径逃逸、URL、大小、嵌套和记录数限制；
- Train/Eval 切分按 Project 和时间，存在自动 Leakage Test。

### 8.4 回归

- V0.1/V0.2 Panorama 全部现有测试继续通过；
- V0.4 Evidence/Studio/Trace/Receipt 行为不变；
- `CONTROL / SYSTEM / EVOLUTION` 三主视图不变；
- Renderer 升级继续证明 Data Hash 不变；
- SKILL.md 保持核心流程精简，详细 Event/Export 合同放在一层 docs/reference；
- 更新 `agents/openai.yaml` 前先核对 Trigger 描述，运行 Skill `quick_validate.py`；
- 完成真实 Git、非 Git、Schema 0.1、Schema 0.2 和 Legacy Backfill 五类 Forward Test。

### 8.5 Projection 与交付证明

- 同一 Core/Event/`asOf` 输入重复编译得到相同 View IR Semantic Hash；
- 未知字段、重复 ID、悬空引用、错误 Binding 和不完整 Event Checkpoint 必须 fail closed；
- exact-ID Delta 不因对象键顺序、数组重排、主题、缩放或纯坐标变化产生 semantic change；
- Entity/Relation/Event/Trace Deep Link 只恢复已存在对象，不创建边、不推断影响；
- 结构化 Evidence Pin 与当前 Git revision 或完整 Source Digest 不匹配时不得激活源码位置；
- Candidate 校验失败时目标制品字节不变，last-good 继续可用；
- Receipt 中自动检查、浏览器证据与人工视觉评审状态相互独立；
- Proof Lab 的输入、View IR、Receipt、HTML 与 Manifest 相互绑定且可在离线环境复核；
- Projection/Delivery 失败不修改正式 Data Hash、Event Store 或 Governance State。

## 10. 风险与控制

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 演化为通用 Agent 平台 | 破坏 Panorama 定位 | Export-only；不内置调度、训练、向量库 |
| 双写不一致 | 状态与事件互相矛盾 | Outbox、Result Binding、fail-closed/补偿分级 |
| Hash 被误当作真实性 | 错误提升证据 | 保留 Authority/Confidence/Freshness |
| 事件体积膨胀 | Single HTML/本地存储失控 | Sidecar、一事件一文件、Checkpoint、Retention |
| Prompt/Secret 泄漏 | 数据集和 RAG 安全风险 | 内容最小化、Redaction、Access Class、Export Scan |
| 时间泄漏 | Eval/训练结果虚高 | asOf 截断、Outcome 隔离、Project-level split |
| 单项目过拟合 | 模型学习 cat-sys 特例 | cat-sys 只作 Pilot；补充多项目 Forward Test |
| Append-only 与删除冲突 | 隐私与合规风险 | Tombstone/Redaction Manifest、真正载荷删除 |
| Schema 过早重构 | 兼容和迁移成本失控 | Sidecar-first；Panorama Schema 延后单独批准 |
| View IR 变成第三套事实源 | Core/Event/Renderer 语义分叉 | 只读、可重算、完整 Binding、禁止反向 Apply |
| 展示质量压过工程真实性 | 漂亮制品掩盖 Unknown/Conflict | inspection 默认；语义门禁先于视觉门禁；视觉状态独立 |
| 源码位置或私有路径泄漏 | Share/RAG 制品扩大暴露面 | revision/digest 精确验证、Access Class、Export 默认移除 |
| 像素 Golden 脆弱 | 跨平台误报和维护成本高 | 语义/几何规则作自动门禁；截图只作人工证据 |
| Delegated Policy 过宽或失控 | Agent 绕过人工治理 | 单 Operation、精确 Scope、Expiry/Use Limit、Revocation、Execution Receipt、fail closed |

本次选择的是与“Agent Skill + 架构认知 + Single HTML”语境最吻合的
[`tt-a1i/archify`](https://github.com/tt-a1i/archify)，不是其他同名仓库。探索绑定稳定版本

dereferenced tag commit 为 `e1ac748f19cf805e44bf74fb93c796662152e273`。

主要依据：

### 11.2 能力对照

| Archify 机制 | Panorama 当前基础 | 判断 | 补全动作 |
| --- | --- | --- | --- |
| 五类严格 Typed JSON IR | 已有正式 Panorama Schema 与 Studio Session，但 Renderer 直接消费大对象 | 部分具备 | 新增一个共享、只读 `panorama-view-ir`，不复制五套事实 Schema |
| authored stable ID + exact-ID Delta | 正式实体和 Studio Diff 已按精确 ID 对齐，关系身份未统一 | 高价值缺口 | SF-35；统一关系身份并泛化到 Event/Projection Delta |
| 结构/几何/制品多层 Validator | 已有 Formal Validator、Presentation Hash 与 Renderer 回归 | 可直接增强 | 将语义验证与派生制品/几何/安全验证分层，不改变 Formal Finding 权威 |
| Machine Repair/Delivery Receipt | Verification Receipt 面向外部测试，缺少 Renderer 交付回执 | 高价值缺口 | SF-36；稳定 rule code、subject、evidence、supported fixes、artifact binding |
| last-good Preview + Candidate 原子替换 | Core Apply 已有锁、备份、CAS 和原子替换；派生视图没有统一合同 | 已有基础 | 复用现有事务思想到派生制品，不另建通用后台服务 |
| Git revision-pinned source evidence | 有 project-level Git/Source Binding；Evidence 字符串只有精确匹配才激活 | 高价值缺口 | 依赖 SF-24 增加结构化 Evidence Pin；非 Git 使用完整 Source Digest |
| Route/Reach/Search/Guided View 不发明拓扑 | 已有 Trace Route、Evidence Inspector 和三主视图边界 | 高度一致 | 仅从正式关系投影稳定 Deep Link；章节是只读引用，不产生新事实 |
| 11 场景、99 checks 的 Proof Lab | 有 Reference Project 与回归测试，缺少输入—IR—Receipt—HTML 的公开证明链 | 高价值缺口 | V0.5.3 建立 Panorama Proof Lab，cat-sys 作为真实纵向场景之一 |
| PNG/SVG/WebM/Share Card 与视觉 Preset | Single HTML 是主制品，Export 尚未形成脱敏分享合同 | 延后且有风险 | V0.6 后按需支持静态 share；不把动画、品牌或主题作为 V0.5 目标 |

### 11.3 应吸收的核心方法

1. **Projection as Code**：正式事实与展示 IR 分离，View IR 严格、版本化、可重算；
2. **Exact Identity First**：差分、Trace、Deep Link 和事件引用都建立在稳定 ID 上；
3. **Validation Receipt First**：每次交付都留下输入绑定、检查列表和明确未完成人工项；
4. **Last-good Delivery**：失败候选不替换已验证制品，也不污染正式状态；
5. **Revision/Digest-pinned Evidence**：源码位置只有在当前绑定得到验证时才可点击或导出；
6. **Proof before Showcase**：用 checked-in 场景、最小输入、输出与回执证明能力，再讨论视觉扩张；
7. **Truthful Interaction**：搜索、路径、Reach、章节只复用已记录关系，绝不从交互行为推断风险或影响。

### 11.4 明确不吸收

- 不用 Archify 替换 Panorama Renderer，也不直接复制其 Schema；两者分别解决“工程治理认知”和
  “技术图示表达”，真相边界不同；
- 不把自然语言系统描述直接物化为 Current，不把 Mermaid 当正式 Evidence；
- 不把公开 GitHub commit 作为唯一 Evidence 模式；Panorama 必须兼容私有 Git、非 Git 和 Access Class；
- 不在 V0.5 引入远程品牌抓取、主题市场、浏览器后台服务、WebM 或默认 Motion；
- 不把自动视觉检查称为人工视觉通过，不把图示 Delta 外推为风险、影响范围、部署真实性或可合并性；
- 不把 named story、route 或 share state 写回 Core/Event，也不允许它绕过 Proposal/Approval/Apply。

### 11.5 补全后的优先级

- P0 合同冻结：SF-24 的 Evidence Pin 补充项、SF-34～SF-36，以及 Proof Lab 验收合同；
- P1（M2 Event Core 稳定后）：View IR、`asOf` Projection、Exact Delta、Delivery Receipt、
  稳定 Deep Link 与 last-good 派生交付；
- P2：脱敏静态 Share Artifact、命名 Event/Trace Chapter、可选人工视觉审阅流；
- 暂不进入路线：独立五图模式、品牌资源、通用布局、WYSIWYG、默认动画、托管分享。

## 13. 组合验证后的修订结论

### 13.1 验证是否足以支撑后续设计

本轮形成 16 份 Schema-valid 运行回执：11 份 `passed`、3 份 `partial`、2 份
`blocked-by-environment`，没有失败的硬门禁。组合覆盖了受控事实回忆、源码拓扑、作者定义 C4、
时序/交互图、TypeScript 依赖、原始 Agent 轨迹、ATIF 互操作、RAG 检索、MLflow 往返、
静态 OTel 拓扑、公开项目和大仓规模边界。

因此，本轮验证**足以批准 M0 设计冻结，并允许 V0.4.1、M1、M2 按门禁分阶段实现**；但它不是
发布认证，也不支持以下结论：完整 Backstage 性能、真实 OTel/GenAI 运行时覆盖、公开多版本演进准确率、
ProjectMind 运行时可用性、完整 Structurizr 工作区无损导入，或数据已适合后训练。

### 13.2 关键实证与设计影响

| 实证 | 观察结果 | 对 V0.5 的约束 |
| --- | --- | --- |
| Panorama / Archify / LikeC4 受控项目 | 三者均覆盖 10/10 预置事实；Archify 经过视口修复后人工视觉通过 | 保留 Panorama 的事实治理；通过 View IR 吸收多视图与交互，不替换 Core |
| dependency-cruiser 受控 TypeScript | 4 条运行依赖和 1 条 type-only 依赖被正确分离；三次语义结果一致 | Extractor Adapter 必须保留依赖种类、解析状态和工具版本，不能把所有 import 扁平化 |
| Backstage 三包切片 | 292 个源码文件、310 个模块、630 条边；稳态约 914 ms | 可作为切片级容量基线；不得外推为完整 Backstage 性能 |
| SWE-agent 原始轨迹 | 12 条消息可合并为 7 个工程事件和 7 个 ATIF step，5 对 tool-call 关系完整保留 | Event Schema 需要多来源 JSON Pointer、工具调用关系和 `timestampPrecision=unknown` |
| cat-sys 纵向轨迹 | 64 条记录可转换并用于 RAG/Eval seed；没有可靠 reward、模型、token 或运行时 span | 区分原始捕获与事后记录；缺失信息必须显式，不得伪造训练标签 |
| Structurizr 作者定义 C4 | 官方 CLI 验证/导出通过；工作区含 62 个元素、43 条关系、11 个视图；原型仅桥接 1 个动态视图 | 增加独立 Model IR / C4 Import Adapter 与 Loss Report；禁止把原型桥接宣称为正式能力 |
| OTel Demo 固定源码切片 | 20 个声明服务、46 条声明依赖、四类 collector pipeline；未运行系统 | 静态声明与运行时观察必须是不同 Evidence Class，`depends_on` 不等于真实调用 |
| 视觉与交付回执 | 自动几何门禁能发现溢出，但不能替代人工审美与可读性判断 | Renderer 保留自动门禁、last-good 制品与独立人工视觉状态 |

### 13.3 Event Schema 修订方向

M0 应把本轮验证形成的 `panorama-event.schema.v0.2` 作为**实验输入**，而不是直接并入正式 Schema。
正式设计至少需要冻结以下语义：

1. `capturedAt` 与可空 `occurredAt` 分离，并用 `timestampPrecision` 表达时间可信度；
2. 一个事件允许绑定多个来源位置，支持文件片段、JSON Pointer、Git revision 与完整目录 digest；
3. 原始 Agent message/tool-call、人工轨迹、治理 Proposal/Approval/Apply、验证回执使用不同
   Evidence Class，但投影到统一 Event Envelope；
4. `informationGaps` 是一等字段；缺少 reward、模型、token、logprobs、运行时 span 时必须保留 Unknown；
5. 训练、评测与 RAG 资格由导出策略计算，不写成事件自身的永久真值；
6. Raw Capture、Post-hoc Record、Derived Projection 三层必须可区分、可追溯、可重新计算；
7. 外部格式适配采用无损优先并生成 Loss Report；ATIF、MLflow、OTel、C4 都不能成为内部主 Schema。

### 13.4 架构和 UI 修订方向

在现有 `Panorama Core → Event Fabric → View IR → Verified Delivery` 路径上增加两类明确适配器：

- `Extractor Adapter`：消费语言/工具特定输出，保存 tool version、source binding、edge kind、
  resolved/unresolved/non-followable 状态；
- `Model Import Adapter`：消费 Structurizr/LikeC4 等作者模型，映射到只读 Model IR，并产出
  element/view/relationship/layout/document/ADR 的保留率和 Loss Report。

UI 不按“多做几张图”推进，而按同一事实模型提供 Architecture、Sequence、Data Flow、Lifecycle、
Evolution/Risk 等 Guided Views。每个视图必须显示来源、时间边界和未知项，支持精确 Deep Link；
交互状态不得反写为工程事实。自动视口检查、窄屏检查和 last-good 交付是发布门禁，人工视觉评审单独记录。

### 13.5 修订后的优先级与退出条件

| 优先级 | 里程碑 | 交付物 | 退出条件 |
| --- | --- | --- | --- |
| P0 | V0.4.1 Readiness + Validation Harness | 回执聚合、隐私扫描、固定 revision/source digest、可复现实验脚本 | 基线测试不回退；所有硬门禁无失败；失败/阻塞证据可追踪 |
| P0 | M0 Design Freeze | Event Envelope、时间语义、Evidence Class、Loss Report、Outbox、Retention 合同 | Schema Findings 全部记录并批准；不修改正式 0.2 数据 |

### 13.6 尚未闭合的验证缺口

- Backstage 只完成 Git tree 规模边界与三包 TypeScript 切片，没有完整仓扫描或端到端 UI 性能；
- OTel Demo 只验证固定源码声明，没有启动系统或采集真实 span；GenAI agent span 仍为零；
- 尚未以至少两个公开项目执行多 commit 演进、freshness drift 和 `asOf` 泄漏测试；
- ProjectMind 只完成源码评审，运行时因环境受阻；CodeBoarding 与 Codebase Memory 同样未形成可比输出；
- Structurizr 原型只保留 1/11 视图的 4 个 participant 和 6 个 message，未保留部署、文档、ADR、布局和图像；
- 当前没有足以支持 SFT/RL 的质量标签、reward、失败归因和许可审计；现有数据只适合作为 Eval seed 与 RAG 实验材料。

### 13.7 最终 Go / No-Go

**Go：** V0.4.1 验证基建、M0 设计冻结、M1/M2 Event Core、适配器合同和 View IR 原型。

**No-Go：** 直接启动后训练、把 RAG 实验结果宣称为生产效果、Renderer 全量重写、完整 C4 无损导入声明、
完整 Backstage 容量声明、未观察的运行时拓扑，以及把本次临时代理审批写入默认产品策略。
